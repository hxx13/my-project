实现方案对比

前端为主 vs 后端为主 vs 混合路线

B

推荐：后端新增1个接口 + 改造2个接口

新增：房间偏好数据接口 | 改造：groups (加活跃度排序/校区/分页)、members (加周频次/经验等级)

A

纯前端方案

所有计算和聚合在浏览器完成，利用现有 API + 人员资料库 API 拼装数据

C

全后端方案

全部在新 Controller 中重新实现，前端仅做展示

对比分析

A 纯前端B 混合（推荐）C 全后端
改动量仅前端 ~6文件前端 ~6 + 后端 ~3文件前端 ~5 + 后端 ~6文件
可维护性⚠ 前端聚合逻辑重✅ 职责清晰✅ 但改动面大
性能❌ 课题组多时前端卡顿✅ 数据库排序+分页✅ 最优
风险高（人员库大批量匹配）中中高（改面大）
并行能力✅ 前后端独立✅ 前端 UI + 后端 API 可并行需前后端串行确认

B 方案的具体接口改造清单

1. 改造 GET /v1/analytics/student-activity/groups

+ 返回 campus、perCapitaActivity（人均活跃度）

+ 按 perCapitaActivity desc 排序

+ 支持 page/size 分页参数

2. 改造 GET /v1/analytics/student-activity/members

+ dailyAvgFreq → weeklyAvgFreq

+ summary.activeRate → activityShare（同校区人均占比）

+ 返回 userLevel 字段（从人员资料库关联）

3. 新增 GET /v1/analytics/student-activity/room-usage

+ 参数: groupName, startTime, endTime

+ 返回: { roomName, entryCount }[] 按次数降序

4. 前端改造

+ ActivityFilterBar: 修复搜索bug + 导出按钮右移 + 组翻页器

+ StudentActivityReportPanel: KPI 标题时间参数化 + 新图表

+ ActivityMemberTable: 经验等级列 + 周频次列

+ ActivityTrendChart → ActivityRoomChart: 改成房间柱状图

+ 人员数据库翻页bug修复
