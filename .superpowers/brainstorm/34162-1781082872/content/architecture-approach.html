架构方案对比：学生物资申领系统

全新独立系统，复用 supplies 业务模式但数据完全隔离

A

全量复制 · 独立模块（推荐）

新建 modules/student-supplies，完整复制 supplies 的业务模式（购物车→申领→审核→出库→流水），使用独立数据库表、独立 API 前缀、独立前端页面。与现有 supplies 模块零耦合。

B

引擎复用 · Schema 注入

抽取 supplies 引擎层（购物车引擎、申领导航、库存流水引擎），通过 Schema 注入区分学生端/管理端。共享核心逻辑但数据分表。灵活性高但增加引擎层抽象成本。

决策理由

选 A 的理由

  • 用户明确要求数据隔离——独立表天然保证
  • 业务逻辑复制代价低——supplies 模式已成熟稳定
  • 学生端和教职工端可独立演进
  • 后期无需担心条件过滤遗漏导致数据泄漏

A 的代价

  • 初始代码量较大（可大幅参考现有 supplies 代码）
  • 两套物资系统并存需在导航层做好区分
