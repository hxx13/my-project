学生活跃度统计 - 三种实现方案

选择架构方案，决定页面在现有系统中如何集成

A

嵌入统计与审计框架（推荐）

在 AnalyticsReportRegistry 注册新报表 student_activity，新建 StudentActivityReportPanel，复用已有配置管理/快照/订阅体系。报表目录左侧栏自然新增一项，与隔离服、笼架报表平级。

优点

  • 复用权限、配置保存、AI解读等基础设施
  • 与现有报表交互一致，用户零学习成本
  • 前端只需新增一个 Panel 组件 + API

缺点

  • 受限于报表框架的 UI 模式
  • 活跃度排序/图表需求与框架通用组件略有差异
B

独立后台页面

新建独立路由 /admin/student-activity，完全自定义的页面布局和后端 API，不受 analytics 框架约束。

优点

  • UI 设计完全自由，可以做复杂的图表交互
  • 后端 API 轻量，不需走快照/清算流程

缺点

  • 权限、配置保存等需重新实现
  • 报表目录不统一，入口分散
  • 与现有统计分析体系割裂
C

混合模式 — 注册报表 + 独立布局

在报表目录注册，但 Panel 内使用自定义布局（不套用 KPI strip + 快照模式），后端走轻量 API 实时查询而非预清算。

优点

  • 入口统一（报表目录），体验独立（定制UI）
  • 实时查询，无需等待快照清算

缺点

  • 破坏框架一致性，后续维护需理解两套模式
  • 不能复用 AI 解读、分享导入等高级功能
