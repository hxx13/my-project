## 1. 概述与上下文

### 1.1 背景

当前学生端（`/student`）采用固定侧栏 + 路由平铺模式：10 个导航项线性排列，每个路由页面独立加载数据。现有 11 个页面，Phases 1-3 预计新增 15+ 页面。线性侧栏和扁平路由面临扩展瓶颈。

### 1.2 目标

将学生端从"侧栏平铺"重构为 **Hub-and-Spoke 模式**：
- 一级导航 ≤6 项（认知负荷上限）
- Hub 页（首页）用 Widget 网格聚合信息，支持预设布局切换（V1 不做拖拽）
- Spoke 页（二级路由）通过面包屑导航，支持深度无限扩展
- 全局命令面板（`⌘K`）作为主导航脊椎，Phase A 即上线
- 全局 Header 承载搜索、通知、消息等跨页面入口

### 1.3 不做的事

- 不改造非学生端的 `/console` 路由（Admin 已有独立架构）
- 不动移动端 `/m/sc` 路由（另行设计）
- 不做实时协作/WebSocket 改造（Phase 3）
- Phase A/B 不做 Widget 拖拽（仅预设布局切换，拖拽推迟到 Phase D）

### 1.4 架构分层总览

```

│                   GlobalShell                        │
```

### 2.3 路由 handle 定义

```ts
// features/student/routes.tsx
interface StudentRouteHandle {
  breadcrumb: string | null;        // null = 不显示面包屑（首页）
  dynamicBreadcrumb?: (params: Record<string, string>) => string;  // #42 → "申领 #42"
  title: string;                    // document.title
  hubParent?: string;               // 归属哪个 Hub（用于 NavRail 高亮）
}

// 示例
{ path: "services/material/:id",
  element: <MaterialDetailPage />,
  handle: {
    breadcrumb: "申领详情",
    dynamicBreadcrumb: ({ id }) => `申领 #${id}`,
    title: "申领详情",
    hubParent: "services",
  }
}
```

### 2.4 面包屑数据来源

- 静态面包屑：route handle 直接提供
- 动态面包屑（如 `#42`）：通过 `dynamicBreadcrumb` 函数，从 URL params 拼出，无需额外 API 请求
- 动态面包屑（如 `203室`）：如果房间名不在 URL params 中，通过 route loader 或 TanStack Query 缓存获取

### 2.5 路由注册方式

`/student/register` 必须绕过 `AuthGuard` 和 `StudentLayout`。在路由配置中作为独立路由存在：

```tsx
// router/index.tsx
// 注册（公开独立路由 — 无 AuthGuard，无 StudentLayout）
{ path: "/student/register", element: <StudentRegisterPage /> },

// 受保护路由群
{
  path: "/student",
  element: <AuthGuard><StudentRouteRoot /></AuthGuard>,
  children: studentRoutes,  // 来自 features/student/routes.tsx
}
```

其中 `StudentRouteRoot` 内部渲染 `<StudentLayout><Outlet /></StudentLayout>`。此结构等价于当前 `router/index.tsx:177-195` 的注册方式，保持不变。

### 3.2 NavRail 行为（修订：click-toggle，放弃 hover 浮层）

```
默认：56px 宽，仅图标
click 非 active 图标：导航到对应 Hub（如 📋 → /student/services）
click 当前 active 图标：展开 200px 浮层（overlay），显示二级菜单
click 浮层内二级项：导航到 Spoke 页，关闭浮层
click 浮层外 / Esc：关闭浮层
键盘：Tab 进入浮层 → focus trap 在浮层内 → Esc 退出
移动端（<1024px）：底部 TabBar（图标 + 文字），不显示浮层 — click 直接导航到 Hub
```

**active-key 解析**：NavRail 通过 `useLocation()` pathname 前缀匹配确定 active 一级项：

```ts
// 路径前缀 → 一级 key 映射
const HUB_PREFIX_MAP: Record<string, string> = {
  '/student/home':                    'home',
  '/student/services':                'services',
  '/student/resources':               'resources',
  '/student/data':                    'data',
  '/student/inbox':                   'inbox',
  '/student/me':                      'me',
};
// 例：/student/services/material/42 → 前缀 /student/services 匹配 → services active
// 路由 handle.hubParent 作为后备覆盖（当路径前缀匹配不够精确时）
```

**click 交互歧义消除**：用户当前在 `/student/home`，点击 📋：
- 📋 不是 active → 导航到 `/student/services`（不展开浮层）
用户当前在 `/student/services`，再次点击 📋：
- 📋 已是 active → 展开浮层（显示申领物品 / 报修申请 / 我的工单等二级菜单）
用户当前在 `/student/services/material`，点击 📋：
- 📋 是 active（路径前缀匹配）→ 展开浮层

**浮层中的"查看全部"**：浮层底部固定显示对应 Hub 页链接（如"服务首页 →"），方便用户进入聚合页。

**徽章数字**：NavRail 图标支持未读计数徽章（红色圆形，最多显示 "99+"）：

| 图标 | 徽章来源 |
|------|---------|
| 🔔（inbox） | `GET /student/dashboard` → `unreadNoticeCount` + 未读消息数 |
| 📋（services） | 待处理工单数（可选，Phase C） |

徽章在浮层展开时自动清除（标记已读），不需要额外的"清除"操作。

### 5.5 Widget 状态机

每个 Widget 经过以下状态流转：

```
INIT ──→ LOADING ──→ SUCCESS ──→ STALE ──→ REFRESHING ──→ SUCCESS
  │          │          │
  │          ├──→ ERROR │
  │          │     │    │
  │          │     └────┤ (retry → LOADING)
  │          │          │
  │          └──→ EMPTY │
  │                    │
  └────────────────────┘
```

每个 Widget 必须覆盖五种渲染状态：`loading` / `empty` / `error` / `data` / `stale`。

## 6. 安全设计

### 6.1 Widget 可见性控制

- Widget 注册表全量存在于前端代码，所有学生用户看到相同 Widget 列表（控制面板中可选）
- Widget **数据**通过后端 API 按当前登录用户过滤，后端不返回其他用户数据
- `todo-card` Widget 中的待办项仅显示当前用户的待办，后端通过 `authContextService.getCurrentUserId()` 过滤

### 6.2 偏好存储安全

- `student_user_preferences` 表按 `user_id` 隔离，API 层强制 `WHERE user_id = currentUser`
- 偏好 JSON blob 不存储敏感信息（密码、token 等），仅存 UI 布局
- JSON blob 不做服务器端 schema 校验（前端自行处理版本兼容）

### 6.3 路由守卫

### 7.1 路由懒加载策略

```ts

const RoomsPage          = lazy(() => import('./pages/student-rooms'));

// Hub 页预加载：用户 click NavRail 图标时，在导航发生前触发预加载
function preloadHub(hubKey: string) {
  const loaderMap: Record<string, () => void> = {
    services:  () => ServiceHubPage.preload(),
    resources: () => ResourceHubPage.preload(),
    data:      () => DataHubPage.preload(),
    inbox:     () => InboxHubPage.preload(),
    me:        () => MeHubPage.preload(),

  loaderMap[hubKey]?.();
```

- **Zustand store**：仅用于 Widget 布局偏好和 UI 状态，不存业务数据
- **URL search params**：Widget 聚焦状态反映在 URL（`/student/home?focus=stats-overview`）

### 8.2 加载策略（L0-L3 分级）

```
L0: Shell（NavRail + Header + Grid 骨架）     → 首次渲染 < 200ms（纯 HTML/CSS）
L1: Above-fold Widget（前 2 行）               → < 1s，独立 Skeleton 占位
L2: Below-fold Widget（需滚动才看到）           → IntersectionObserver 触发加载
L3: 不可见 Widget（用户在面板中关闭的）          → 不加载，不发起网络请求
```

**实现**：
- L1 Widget 同步渲染 + 各自独立 `useQuery`
- L2 Widget 用 `react-intersection-observer`，`threshold: 0.1` 时触发首次加载
- L3 Widget 的 `enabled: false` 跳过 `useQuery` 的 `enabled` 参数
- 所有 Widget 各自包裹 `ErrorBoundary`，一个 Widget 崩溃不影响其他

### 8.3 Widget 错误隔离

```tsx
// 每个 WidgetCard 都有一个 ErrorBoundary
<ErrorBoundary fallback={<WidgetErrorCard onRetry={refetch} />}>
  <Suspense fallback={<WidgetSkeleton size={size} />}>
    <StatsOverviewWidget size={size} isVisible={isVisible} />
  </Suspense>
</ErrorBoundary>
```

## 9. 边缘情况

| # | 场景 | 处理方式 |
|---|------|---------|
| 1 | **所有 Widget 数据为空**（新注册学生首次登录） | 每个 Widget 各自显示 Empty 引导态，不隐藏 Widget 本身，防止首页变成白板。`profile-card` 显示已填写的注册信息；`stats-overview` 空态显示"欢迎！这是你的第一天"；`pinned-rooms` 空态显示"你还没有房间权限，联系管理员申请"。**首次体验策略**：`profile-card` Widget 中未完善的资料项（如手机号为空）显示"完善资料"引导链接 → 跳转 `/student/me/profile`。不强制要求用户先完善资料才能看首页（允许先浏览，后完善）。 |
| 2 | **单个 Widget 加载失败** | ErrorBoundary 捕获，Widget 卡片显示"加载失败 [重试]"，不影响其他 Widget |
| 3 | **网络断开** | TanStack Query `networkMode: 'offlineFirst'`，stale 数据未过期则展示缓存 + 顶部黄色横幅"网络异常，显示的是缓存数据" |
| 4 | **localStorage 已满**（5MB 配额） | Widget 布局写入前检查 `navigator.storage.estimate()`；写入失败时仅使用内存中的布局，不弹错误提示，后端同步正常进行 |
| 5 | **浏览器后退按钮** | 面包屑导航利用 React Router 的 `useNavigation` + `POP` 事件保持一致性。深层 Spoke → 父 Hub 的后退行为通过路由层级自动处理（React Router 原生行为） |
| 6 | **新旧布局并行**（feature flag 开启前） | `StudentLayout` 根据 feature flag 切换 `NavRail` 或 `StudentSidebar`，两个组件共享相同的 `<Outlet />`，页面代码完全不受影响 |
| 7 | **URL 兼容** | 旧 URL `/student/records` 过渡期保留，通过重定向规则 301 → `/student/data/records`，在 `routes.tsx` 中配置 `redirect` 数组 |
| 8 | **NavRail 浮层 + 键盘焦点陷阱** | 浮层打开时 `focus-trap` 限制 Tab 在浮层内循环，Esc 关闭浮层并归还焦点到触发按钮，浮层外元素 `aria-hidden="true"` |
| 9 | **移动端 NavRail 降级为 TabBar** | `window.matchMedia('(max-width: 1023px)')` 切换布局。TabBar 仅显示图标 + 短文字（6 项平铺），不展示浮层。Hub 页在移动端降级为列表布局 |
| 10 | **Widget 布局数据版本不兼容** | 前端存储时附带 `version: 1` 字段。读取时版本不匹配 → 重置为默认布局 + toast 提示"布局已更新，已恢复默认排列" |
| 11 | **并发：用户同时在两个标签页改布局** | `BroadcastChannel API` 或 `storage` 事件监听，收到远端变更时同步 Zustand store（不覆盖用户正在进行的操作，仅在 idle 时同步） |
| 12 | **长时间停留 Hub 页，Widget 数据过期** | 每个 Widget 独立设置 `refetchInterval: 5 * 60 * 1000`（5 分钟），用户切回浏览器标签页时 `refetchOnWindowFocus: true` 触发刷新 |

|------|---------|

**每个 Spoke 页面必须有一个 `<h1>`**，用于：(a) 路由切换后 focus 目标，(b) 无障碍页面标识，(c) 面包屑的最后一级文本应与 `<h1>` 一致。

```ts
// 每次路由切换后，focus 跳到内容区的 <h1>
useEffect(() => {

  h1?.focus();

```

## 16. Widget 间通信

### 16.1 通信协议

**Widget 之间不直接通信。** 所有跨 Widget 的数据共享通过以下三层：

| 层 | 机制 | 场景 |
|----|------|------|
| TanStack Query 缓存 | 两个 Widget 调用同一 API → 自动共享缓存 | `pinned-rooms` 和 `recent-records` 都展示房间数据 |
| URL search params | Widget A 点击 → 更新 URL → Widget B 读取 URL | 从通知跳转到首页并聚焦特定 Widget：`/student/home?focus=stats-overview` |
| Zustand store | Widget 之间共享的 UI 状态（仅限布局/偏好，不共享业务数据） | Widget 显示/隐藏状态 |

### 16.2 不做的事

- 不引入事件总线（EventEmitter）
- Widget 不互相导入对方的 Hook
- Widget 不通过 prop drilling 传递数据

## 21. 扩展模式

未来新增功能只需三步：

1. **创建 Spoke 页面**：写正常的页面组件 + hooks
2. **注册路由**：在 `routes.tsx` 添加路由 + handle（面包屑自动渲染）
3. **注册 Hub 入口**（可选）：`registry.register({ hubId, entry })` → 自动出现在对应 Hub 页

无需改动 NavRail、Header、Layout、API 层。

## 22. 迁移策略

### 22.1 迁移原则

- 增量重构，新旧布局共存过渡
- 先建新、再迁旧、最后删旧
- 每个 Phase 独立上线

### 22.2 Phase A：新骨架 + 命令面板（~3 天）

1. 后端（详见 §4）：1 个 SQL 迁移文件（`student_user_preferences` 表）+ 1 个 Controller + 1 个 Service + 1 个 Mapper + 2 个 Feature Flag 配置项
2. 新建 `nav-rail` + `nav-flyout` + `breadcrumb-bar`
3. 新建 `global-search` 命令面板（`⌘K`）
4. 重构 `student-layout`：引入 NavRail + BreadcrumbBar + 新 Content 区
5. 保留 `student-sidebar` + 所有现有页面，通过 `student.nav_rail` flag 切换新旧布局

### 22.3 Phase B：首页 Hub 改造（~3 天）

1. 将 `student-home.tsx` 拆为多个 Widget 组件（见 §19.2，共 10 个：6 个拆分自现有首页 + 2 个现有功能迁移 + 2 个新增）
2. 新建 `widget-grid` + `widget-card` + `widget-panel` + `widget-error-boundary`
3. 实现 3 种预设布局切换（**不做拖拽**）
4. 实现 Widget 布局 persist（localStorage + 后端）
5. `student.hub_widgets` flag 灰度
6. 数据层不变（Widget 复用现有 hooks）

### 22.4 Phase C：路由重组（~2 天）

1. 建立路由层级（Hub → Spoke）
2. 添加面包屑 handle
3. 旧 URL 301 重定向
4. 非首页 Hub 页实现（ServiceHub / ResourceHub / DataHub / InboxHub / MeHub）

### 22.5 Phase D：增量丰富（持续）

1. 新页面按 Spoke 模式接入
2. Widget 拖拽（引入 `@dnd-kit`）
3. 搜索源扩展（工单号、申领号）
4. 合规数据接入

### 22.6 Feature Flag

```ts
export const STUDENT_NAV_RAIL    = 'student.nav_rail';     // Phase A
export const STUDENT_HUB_WIDGETS = 'student.hub_widgets';  // Phase B
```

通过 `fetchPublicRuntimeConfig()` 读取，支持按用户/角色灰度。

## 23. 技术选型

| 需求 | 选择 | 理由 |
|------|------|------|
| 导航浮层 | 自定义（Radix Popover 或纯 CSS） | 无需额外依赖 |
| 命令面板 | 自定义（Radix Dialog + input） | 避免 cmdk 依赖，逻辑简单 |
| 预设布局 | CSS Grid `grid-template-areas` 切换 | 无需 @dnd-kit（Phase D 再引入） |
| 拖拽（Phase D） | `@dnd-kit/core` + `@dnd-kit/sortable` | 轻量、无障碍、React 原生 |
| Widget 布局 persist | localStorage + `/api/student/preferences` | 即时响应 + 跨设备同步 |
| Feature Flag | 复用现有 `fetchPublicRuntimeConfig` | 已有基础设施 |
| 动画 | 现有 GSAP + CSS transition | 不引入新库 |
| 响应式网格 | CSS Grid + `auto-fit / minmax` | 原生、高性能 |

## 24. 风险表

| 风险 | 严重度 | 缓解措施 |
|------|--------|---------|
| 重构引入回归 bug | 高 | Feature flag 灰度，旧布局保留至验证通过 |
| 浏览器后退按钮行为异常（SPA 多层路由） | 中 | React Router v7 原生嵌套路由处理 POP 事件；集成测试覆盖 3 层深度后退 |
| 9 个 Widget 同时加载性能（低端设备） | 中 | L0-L3 加载分级；L2 Widget 用 IntersectionObserver 延迟；性能预算监控 |
| iPad + 键盘用户的焦点陷阱 | 中 | focus-trap 库确保浮层内 Tab 循环；Esc 关闭浮层并归还焦点 |
| localStorage 配额超限（5MB） | 低 | 写入前 `navigator.storage.estimate()` 检查；后端同步为权威数据源 |
| 每个用户不同布局 → 客服无法复现 | 低 | 客服管理端可查看/重置学生布局；URL `?layout-reset=true` 快捷重置 |
| @dnd-kit React 19 兼容性（Phase D） | 低 | Phase D 引入前验证；备选：CSS Grid 手动排列 |
| Widget 版本不兼容导致白屏 | 低 | 布局数据带 `version` 字段；version mismatch → 自动重置默认布局 + toast 通知 |

## 25. 设计决策记录

### 决策 1：侧栏 vs 顶部导航

**选型**：侧栏 NavRail（56px 图标）。
**理由**：(a) 目标用户（高校学生）习惯侧栏导航；(b) 侧栏不占内容垂直空间；(c) click-toggle 浮层替代 hover。
**拒绝**：顶部 TabBar — 一级 ≤5 项，不适合深度扩展。

### 决策 2：Widget 网格 vs 固定布局

**选型**：预设布局切换（V1），未来拖拽（Phase D）。
**理由**：(a) V1 不需要 @dnd-kit 依赖；(b) 3 种预设覆盖 90% 场景；(c) 拖拽是 polish 功能，不是 V1 刚需。
**拒绝**：固定仪表盘 — 无法个性化。
**拒绝**：V1 就做拖拽 — Google Analytics / iOS Widget V1 都没有拖拽。

### 决策 3：click-toggle vs hover 浮层

**选型**：click-toggle 浮层。
**理由**：(a) 触屏兼容；(b) 光标漂移问题；(c) Apple HIG + Material Design 3 推荐。
**拒绝**：hover 浮层 — 触屏不可用，光标漂移令人沮丧。

### 决策 4：命令面板 Phase A 就做

**选型**：`⌘K` 命令面板在 Phase A 上线。
**理由**：(a) Hub-and-Spoke 深层导航需要快速入口；(b) Linear/Notion/VS Code 的脊椎功能；(c) 纯前端实现，零后端依赖。
**拒绝**：推迟到 Phase D — 会导致深层导航体验差，用户在 3 层面包屑中迷路。
