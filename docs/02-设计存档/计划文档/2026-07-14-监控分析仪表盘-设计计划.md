# Monitor Analytics — GoAccess 风格仪表盘

> **版本**: v1.1（三 Agent 交叉审查修正版） | **日期**: 2026-07-14 | **目标**: 在前端 `/#/console/admin/monitor` 页面中实现类似 GoAccess 的访问统计面板，零外部依赖
>
> **已知限制**：所有计数存储在 JVM 堆内存中，JVM 重启后所有计数器归零。分析数据是进程级运维快照而非持久化业务数据。如需历史趋势，参见第五节扩展方案。

## 二、方案设计

### 架构

```
浏览器请求
    │
    ▼
RequestMetricsInterceptor (新建)
    ├── 原子累加状态码计数
    ├── 原子累加 URI 计数
    ├── 原子累加 IP 计数
    └── 记录 uniqueVisitor

定期轮询 (5min)
    │
    ▼
GET /api/v1/monitor/analytics (新增)
    │
    ▼
MonitorController → RequestMetricsInterceptor → 返回聚合数据
    │
    ▼
MonitorAnalyticsCards.tsx (新建) → MonitorDashboardPage Overview tab
```

### 设计决策记录

| 决策 | 选择 | 理由 |
|------|------|------|
| 存储方式 | JVM 内存（`ConcurrentHashMap`） | 分析数据是进程级运维快照，非持久化业务数据。重启归零可接受——监控仪表盘显示"自本次进程启动以来"。历史趋势由第五节定时快照方案覆盖 |
| 轮询 vs WebSocket | 5 分钟轮询 | 分析聚合数据变化缓慢（分钟级），不需要 Socket.IO 实时推送的毫秒级延迟。轮询比推送简单可靠，且减少 WebSocket 连接开销 |
| 复位模式 | 不复用 `SchedulerBootstrapRunner` | analytics 不需要对齐"错过/冻结"的任务概念；唯一访客的日重置用简单的 `@Scheduled` + `stream().filter(today::equals)` 更清晰 |

### 后端：RequestMetricsInterceptor

路径：`src/main/java/com/example/demo/common/config/RequestMetricsInterceptor.java`

职责：每个 HTTP 请求在 `afterCompletion()` 中按维度原子累加。使用 `ConcurrentHashMap<String, LongAdder>` 实现零锁竞争。

**内部数据结构**：

```java
// 状态码分布
ConcurrentHashMap<String, LongAdder> statusCounts  // "200"→4891, "404"→312

// Top URLs（归一化后路径，不含参数/UUID/数字ID）
ConcurrentHashMap<String, LongAdder> urlCounts     // "/api/client-version"→1203
static final int MAX_URL_ENTRIES = 10000;           // 硬上限，超出拒绝新key

// 响应时间分桶（毫秒）
ConcurrentHashMap<String, LongAdder> responseTimeBuckets
// "0-10"→82341, "10-50"→15203, "50-100"→3102, "100-200"→891,
// "200-500"→234, "500-1000"→45, "1000-3000"→12, "3000+"→3

// Top 访客 User-Agent（截断至 80 字符，无隐私问题）
ConcurrentHashMap<String, LongAdder> uaCounts     // "Mozilla/5.0...Chrome/149.0.0.0"→3241

// 总数
LongAdder totalRequests

// 独立访客（IP→最后访问日期，每日凌晨3点清理非今日条目）
ConcurrentHashMap<String, LocalDate> uniqueVisitors
```

> **前置检查**：每日清理依赖 `@Scheduled`。确认 `TwinSystemApplication` 或任一 `@Configuration` 类上有 `@EnableScheduling`（本项目已有 `JobSchedulerService` 使用定时任务）。如未启用，在任意 `@Configuration` 类上添加即可。

**URL 归一化策略**（防止 UUID/参数/数字 ID 导致 HashMap 无限膨胀）：

```java
private String normalizeUrl(String requestUri) {
    return requestUri
        .replaceAll("/[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}", "/{uuid}") // UUID
        .replaceAll("/[0-9a-f]{24}", "/{objectId}")   // MongoDB ObjectId
        .replaceAll("/\\d{10,}", "/{timestamp}")       // Unix 时间戳
        .replaceAll("/\\d+", "/{id}");                 // 普通数字 ID
}
```

**容量安全**：插入前检查 `urlCounts.size() < MAX_URL_ENTRIES`，超出则 `log.warn` 并跳过。防止攻击者用随机路径刷爆内存。

**异常安全**：整个 `afterCompletion()` 包裹在 `try-catch(Throwable)` 中，采集失败只记日志，不影响原始请求。

**对外接口**：`getSnapshot()` → 遍历 `ConcurrentHashMap` 返回不可变副本。**注意**：`ConcurrentHashMap` 的弱一致性迭代器可能导致快照与真实值偏差 < 0.1%，对监控用途可接受。

**WebMvcConfig 注册**（排除自身和公共路径）：
```java
registry.addInterceptor(requestMetricsInterceptor)
        .addPathPatterns("/api/**")
        .excludePathPatterns(
            "/api/v1/monitor/**",   // 避免自计数
            "/api/auth/**",         // 与 ApiAuthInterceptor 排除项对齐
            "/api/public/**"
        );
```

### 后端：MonitorController 新增端点

在 `MonitorController.java` 中新增：

```java
private final RequestMetricsInterceptor requestMetricsInterceptor;

@GetMapping("/analytics")
public Result<Map<String, Object>> analytics(
        @RequestHeader(value = "Authorization", required = false) String authorization) {
    Result<?> denied = requireAdmin(authorization);
    if (denied != null) return (Result<Map<String, Object>>) denied;

    Map<String, Object> data = new LinkedHashMap<>();
    RequestMetricsInterceptor.Snapshot s = requestMetricsInterceptor.getSnapshot();
    data.put("totalRequests", s.totalRequests());
    data.put("uniqueVisitors", s.uniqueVisitorCount());
    data.put("statusDistribution", s.statusDistribution());
    data.put("topUrls", s.topUrls(10));
    data.put("top404Urls", s.top404Urls(10));
    data.put("topUserAgents", s.topUserAgents(5));
    data.put("responseTimeBuckets", s.responseTimeBuckets());
    return Result.success(data);
}
```

**响应示例**：

## 三、前端改动

### 3.1 `monitor.api.ts` — 新增类型 + API

```typescript
export interface AnalyticsSnapshot {
  totalRequests: number;
  uniqueVisitors: number;
  statusDistribution: Record<string, number>;
  responseTimeBuckets: Record<string, number>;
  topUrls: Array<{ path: string; count: number }>;
  top404Urls: Array<{ path: string; count: number }>;
  topUserAgents: Array<{ ua: string; count: number }>;
}

export function fetchMonitorAnalytics(): Promise<AnalyticsSnapshot> {
  // 注意: authHttp 响应形状为 { data: { data: AnalyticsSnapshot } }
  // 需要解包两层: axios data 层 + Result data 层
  // 兼容 authHttp 是否有响应拦截器自动解包 Result<T>
  return authHttp.get('/v1/monitor/analytics').then(r => {
    const wrapper = (r as any).data ?? r;
    return (wrapper?.data ?? wrapper) as AnalyticsSnapshot;
  });
}
```

### 3.2 `useMonitorStore.ts` — 新增状态

```typescript
// 与现有 health/resources/jobs 模块对齐：所有数据模块都有 loading 状态
analytics: null as AnalyticsSnapshot | null,
analyticsLoading: true,           // 初始 true = "正在加载"
analyticsError: null as string | null,

fetchAnalytics: async () => {
  set({ analyticsLoading: true, analyticsError: null });
  try {
    const analytics = await fetchMonitorAnalytics();
    set({ analytics, analyticsLoading: false });
  } catch (e: any) {
    set({ analyticsError: e?.message || '加载分析数据失败', analyticsLoading: false });
  }
}
```

### 3.3 `MonitorAnalyticsCards.tsx` — 新建可视化组件

使用现有纯 CSS 模式（与 `Gauge`/`InfoCard` 一致），不引入新图表库。

**组件状态覆盖（5 态）**：

| 状态 | 触发条件 | 视觉形式 |
|------|---------|---------|
| **Loading** | `analyticsLoading === true && analytics === null` | Skeleton 骨架卡片（对齐 `MonitorSkeleton.tsx` 模式），不显示空白 |
| **Error** | `analyticsError !== null` | **模块级降级**：红色边框的错误提示卡片，不影响页面其他模块（对齐 `MonitorHealthCards` 第 293-298 行模式） |
| **Empty** | `totalRequests === 0`（JVM 刚重启） | 引导文字："拦截器已就绪，等待首个请求后开始统计"（非"暂无数据"） |
| **Normal** | 数据正常 | 大数字 + 分段进度条 + 排名列表 |
| **Partial** | `totalRequests > 0` 但 `topUrls` 为空等 | 缺失模块显示"暂无足够数据生成排名"，不影响有数据的模块 |

**数据展示模块**：

| 模块 | 视觉形式 | 实现 |
|------|---------|------|
| 总请求数 | 大数字 + 标签 | 同 InfoCard |
| 独立访客 | 大数字 + 标签 | 同 InfoCard |
| 200 率 | 百分比 + 绿色分段条 | CSS 进度条，色值来自 `--app-color-feedback-success` |
| 500 数 | 红色数字（0 则绿色），背景 `--app-color-feedback-danger-soft` | 确保对比度 ≥4.5:1 |
| 状态码分布 | 多色分段进度条 | CSS flex 条，200=success / 404=warning / 500=danger 令牌，自动跟随 light/dark 双模 |
| 响应时间分布 | 分桶直方图 | CSS 横向条形图，8 个桶从"0-10ms"到"3000+ms" |
| Top 5 URLs | 排名列表 | `<ol>` 语义化列表，序号 + 路径 + 右侧计数 |
| Top 5 404 URLs | 排名列表 | 同上，数据源为 `top404Urls` |
| Top 5 User-Agent | 排名列表 | `<ol>` 语义化列表，显示 UA 前 60 字符 + 右侧计数 |

**可访问性**：
- 多色分段进度条：`role="progressbar"` + `aria-valuenow` + `aria-valuemax` + `aria-valuetext`（如 "200 响应占 92.5%，404 响应占 5.9%，500 响应占 1.6%"）
- 排名列表：使用 `<ol>` 语义标签（顺序有意义），非手动编号文本
- 响应时间条形图：`role="img"` + `aria-label` 描述分布

**设计方向说明**：当前为大数字卡片 + 排名列表的 Dashboard 风格（受 GoAccess **启发**但非终端表格复刻）。本文档标题"GoAccess 风格"指灵感来源——数据分析维度（状态码分布、Top URLs、独立访客等）参考了 GoAccess 面板，视觉形式选择的是更适合管理后台的卡片布局。

### 3.4 `MonitorDashboardPage.tsx` — 集成

在 Overview tab 中，`<MonitorResourceGauges />` 下方加入：

```tsx
<div className="analytics-section">
  <MonitorAnalyticsCards />
</div>
```

刷新策略：
- **首次加载**：组件挂载时立即调用 `fetchAnalytics()`（使用 `loadedRef` 模式，参考现有 `MonitorDashboardPage.tsx` 第 86-92 行）
- **后续轮询**：每 5 分钟（300,000ms）自动拉取一次
- **轮询间隔设计理由**：分析聚合数据变化缓慢（分钟级），不需要 15s/30s 高频轮询。5 分钟间隔对分析场景足够且减少带宽浪费

Store 读取方式：使用 selector 精确订阅以避免无关渲染：
```tsx
const analytics = useMonitorStore(s => s.analytics);
const analyticsLoading = useMonitorStore(s => s.analyticsLoading);
const analyticsError = useMonitorStore(s => s.analyticsError);
const fetchAnalytics = useMonitorStore(s => s.fetchAnalytics);
```

## 六、后续可扩展

| 方向 | 做法 | 依赖 | 需要 DB？ |
|------|------|------|---------|
| 按小时/天的趋势图 | `ScheduledExecutorService` 每 5 分钟拍 `getSnapshot()` → 内存环形缓冲区（保留 24 小时）→ Recharts 折线图 | v1 拦截器已就绪 | **否** |
| 慢 API 排行 | v1 拦截器在 `preHandle()` 中已记录 `startTime`（`request.setAttribute("req.startTime", System.nanoTime())`）→ `afterCompletion()` 中计算耗时 → 聚合到 `ConcurrentHashMap<String, LongAdder> urlLatencies` | 仅需在 v1 拦截器中加 `startTime` 属性（4 行代码） | **否** |
| 实时 WebSocket 推送 | `socketIOServer.broadcast("analytics:update", snapshot)`，1 行代码 | 高频需求时 | **否** |
| 浏览器/OS 统计 | User-Agent 解析 → 分桶聚合 | 需引入 UA 解析库（如 `ua-parser`） | 否 |
| 地理位置 | IP 地理数据库离线查询 | 需引入 GeoIP 库（如 MaxMind GeoLite2） | 否 |
| 持久化历史数据 | 定时 snapshot 写入 `sys_analytics_hourly` 表 | 需求明确后 | **是** |
