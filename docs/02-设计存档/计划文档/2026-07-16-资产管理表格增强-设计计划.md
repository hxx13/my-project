## 二、问题诊断

### 2.1 批量删除缺失（用户报告）

**现状**: 只有单条删除（`DELETE /v1/assets/{id}`）和清空全部（`DELETE /v1/assets`），不能勾选多行批量删除。

**根因**: 后端无 `batchDelete` 端点，前端无复选框列。

### 2.2 导入表头匹配缺陷（用户报告）

**现状**: 后端 `findHeader()` 对 Excel **源列名**做精确匹配，匹配不到就自动创建新列。

**问题链条**:
1. 用户在 Excel 中使用"当前存放地点"作为表头（这是前端的**显示名**，而非数据列的真实 `column_key`）
2. 后端匹配不到 → 自动创建 `column_label="当前存放地点"` 的新列
3. 数据库同时存在 `column_key="col_存放地点1"`（原列）和 `column_key="col_当前存放地点"`（误创建列）
4. 前端 `normalizeColumnLabel()` 把 `存放地点\d+` 统一显示为"当前存放地点"
5. 结果：两个列显示同名但数据写入不同列 → 数据分散、查询不全

**根因**: 
- 导入匹配使用源表头 + 未命中自动建列（不安全）
- `normalizeColumnLabel()` 过度规范化，掩盖了列差异
- 缺少按 `column_label` 映射到已有列的能力

### 2.3 "当前存放地点"重复列（用户报告）

**根因**: 上述 2.2 问题导致 `asset_column_def` 表中已存在两条记录：
- `column_key="col_存放地点1"`, `column_label="存放地点1"`（原有）
- `column_key="col_当前存放地点"`, `column_label="当前存放地点"`（误创建，`sort_order` 较大）

用户要求删除第二个（按 `sort_order` 排序后的第二个）。

### 2.4 大量保存时页面卡死（用户报告）

**根因链路**:

```
前端 finishEditing() (AdminAssetRecordPage.tsx)
  → for (const [id, patch] of editingDiffs.entries())
      → await patchAssetRecord(id, patchBody)   ← 逐行串行 await
          → POST /v1/assets/{id} (每个请求 ~200ms)
200行编辑 = 200次串行HTTP调用 ≈ 40秒阻塞
```

| 瓶颈点 | 详情 |
|--------|------|
| **前端串行提交** | `editingDiffs` Map 逐条 `await`，200行 = 200次顺序 HTTP |
| **无批量 API** | 后端只有 `PATCH /api/v1/assets/{id}` 单条更新，无 `PATCH /api/v1/assets/batch` |
| **无乐观更新** | 用户必须等待全部 API 完成才能看到结果 |
| **UI 线程阻塞** | 连续 await 阻塞事件循环，页面无响应 |

### 2.5 导入大量文件时超时误报（用户报告）

**根因链路**:

```
前端 useImportAssetExcel()
  → importAssetExcel(file)
      → authHttp.post('/v1/assets/import', formData)  ← 默认 20s 超时
          → 后端 AssetService.importAssetsFromExcel() ← 同步 POI 解析大文件
```

| 瓶颈点 | 详情 |
|--------|------|
| **前端超时过短** | `authHttp` 默认 20s，导入未覆盖为更长超时 |
| **对比其他模块** | `accessFusion` 设为 180s，`dahuaSwingStats` 设为 600s |
| **后端同步处理** | 大文件 POI 解析 + N 次 DB upsert 超过 20s |
| **超时≠失败** | 前端 axios 超时抛错 → 显示"导入失败"，但后端事务已提交、数据已入库 |

## 三、方案设计

### 3.1 架构总览

```

│                               + 查找替换对话框 + 列隐藏/冻结

│                               / deleteByBatch / searchReplace API

├── AssetController.java      ← 新增端点: batch-delete / batch-update / import-preview
│                               / import-batches / delete-by-batch / search-replace
├── AssetService.java         ← 批量操作逻辑 + 导入匹配修复 + 批次追踪
│                               + 查找替换 + 导入预览
├── AssetMapper.java/.xml     ← 新增 SQL: 批量操作 + 批次查询 + 查找替换
```

### 3.2 设计决策记录

| 决策 | 选择 | 理由 |
|------|------|------|
| 批量删除实现 | 后端 `DELETE /batch` 接收 `{ids: []}` | REST 惯例，一次 SQL `IN` 子句完成 |
| 批量更新实现 | 后端 `PATCH /batch` 接收 `{ids: [], values: {}}` | 一次 SQL UPDATE 统一设值，避免 N 次调用 |
| 导入匹配策略 | 改为按 `column_label` 映射，未匹配的**拒绝并返回警告** | 防止自动创建垃圾列，用户可看到哪些列被跳过 |
| 导入预览 | 后端新 `POST /import/preview` 端点返回匹配结果，确认后调用 `POST /import` | 两步式：先预览后确认，用户可在确认前修正 |
| 保存性能 | 前端改为 `Promise.all()` 并发 + 后端新增 `PATCH /batch` | 200 并发 ~2s 完成，batch 端点更只需 1 次调用 |
| 导入超时 | 前端 `authHttp` 对导入端点覆盖 `timeout: 300_000` (5分钟) | 对齐 `dahuaSwingStats` 的 600s 模式 |
| 导入批次表 | 独立表 `asset_import_batch`，导入时写入 batch_id | 最小侵入，不影响现有 upsert 逻辑 |
| 查找替换 | 后端新端点 `POST /search-replace` 直接 SQL UPDATE | 前端不拉全量数据再循环替换 |
| 列隐藏/冻结 | 纯前端 localStorage 存储用户偏好 | 个人视图偏好，不需要后端参与 |
| `normalizeColumnLabel` | 移除正则替换，改为展示原始 `column_label` | 避免掩盖列差异，用户看到的和数据库一致 |

### 3.3 后端新增端点

| 方法 | 路径 | 请求体 | 响应 | 说明 |
|------|------|--------|------|------|
| `DELETE` | `/v1/assets/batch` | `{ids: string[]}` | `{deletedCount: N}` | 批量软删除（后端按500条分批执行，SQL加 `WHERE deleted=0` 防幂等覆盖） |
| `PATCH` | `/v1/assets/batch` | `{ids: string[], fixedFields?: {...}, dynamicValues?: Record<string,string>}` | `{updatedCount: N}` | 批量修改，固定字段 + 动态值分开发送，columnKey 白名单校验 |
| `POST` | `/v1/assets/import/preview` | MultipartFile | `{previewId, columns, sample, warnings: [{header, reason}]}` | 导入预览（不写入），返回 previewId 供确认步骤使用 |
| `POST` | `/v1/assets/import/confirm` | `{previewId, createNewColumns?: string[]}` | `{created, updated, skipped}` | 确认导入（使用 previewId 缓存结果），可选创建用户勾选的新列 |
| `GET` | `/v1/assets/import-batches` | page/size 参数 | `{list: [...], total: N}` | 导入批次历史分页 |
| `DELETE` | `/v1/assets/by-batch/{batchId}` | — | `{deletedCount: N}` | 按批次软删除（仅删除 `created_by_batch_id = batchId` 的资产） |
| `POST` | `/v1/assets/search-replace` | `{columnKey, search, replace, matchMode: "exact"\|"contains"\|"startsWith"}` | `{replacedCount: N}` | 查找替换，columnKey 白名单校验 |

### 3.5 批量保存性能修复

**状态变量正名**：实际代码使用 `editing: Record<string, string>`（key 格式 `rowId::columnKey`），非 `editingDiffs`。以下伪代码已对齐实际数据结构。

**前端 `finishEditing()` 改造**:

```typescript
import pLimit from 'p-limit';

// 旧: for (const key of Object.keys(editing)) { await patchAssetRecord(id, body); }  ← 串行阻塞
// 新:
const limit = pLimit(6);  // 浏览器 HTTP/1.1 兼容（6并发连接）
const patches = buildPatchesFromEditing(editing);  // 聚合同行多字段修改
await Promise.all(patches.map(([id, body]) =>
  limit(() => patchAssetRecord(id, body))
));
// 后端支持后切换为:
// await batchUpdateAssets({ ids: patches.map(p => p[0]), ... });
```

**效果**: 200行编辑从 40s 串行 → ~2-3s 受控并发（6连接 × ~200ms/请求）。

**并发编辑+删除防护**：后端 `updateAssetBase` SQL 的 WHERE 子句加入 `AND deleted = 0`，防止对已删除资产写入僵尸数据。PATCH 端点返回错误信息当资产已被删除时。

### 3.6 导入超时修复 + import_batch_id 策略

**超时修复**（`asset.api.ts`）:

```typescript
const IMPORT_TIMEOUT = 300_000; // 5分钟，对齐 dahuaSwingStats 600s 模式

// 导入预览端点
export async function previewImport(file: File): Promise<ImportPreview> {
  const form = new FormData();
  form.append("file", file);
  return authHttp.post("/v1/assets/import/preview", form, { timeout: IMPORT_TIMEOUT }).then(r => r.data);
}

// 导入确认端点
export async function confirmImport(previewId: string, createNewColumns?: string[]): Promise<ImportResult> {
  return authHttp.post("/v1/assets/import/confirm", { previewId, createNewColumns }, { timeout: IMPORT_TIMEOUT }).then(r => r.data);
}
```

**`import_batch_id` 策略（防覆盖）**:

- `asset_record.import_batch_id` 语义：**仅在 INSERT（新建资产）时写入**，UPDATE（更新已有资产）时**不覆盖**
- 列名建议改为 `created_by_batch_id`，语义明确
- 按批次删除：`WHERE created_by_batch_id = ? AND deleted = 0`
- 此策略避免"资产被两批次导入后，删除旧批次漏删"的问题
- AssetService 中实现：`if (existing == null) { asset.setCreatedByBatchId(batchId); insert(asset); }`

### 3.7 "当前存放地点"重复列清理

**⚠️ 高风险操作 — 必须遵循以下步骤，不可跳过**：

**Step 1: 动态发现重复列**（不硬编码 key，因为 `buildColumnKey()` 的输出取决于当时的 label 精确值）

```sql
-- 查找所有与"存放地点"相关的列定义
SELECT id, column_key, column_label, sort_order
FROM asset_column_def
WHERE column_label LIKE '%存放地点%' OR column_key LIKE '%存放地点%'
ORDER BY sort_order ASC;
```

**Step 2: 数据迁移（先迁后删）**

```sql
-- 假设查询结果: key_keep='col_存放地点1' (sort_order较小), key_delete='col_当前存放地点' (sort_order较大)
-- 2a. 将待删 key 的数据合并到保留 key（保留 key 已有的值优先，不覆盖）
INSERT INTO asset_record_value (asset_id, column_key, column_value)
SELECT v.asset_id, 'col_存放地点1', v.column_value
FROM asset_record_value v
WHERE v.column_key = 'col_当前存放地点'
  AND NOT EXISTS (
    SELECT 1 FROM asset_record_value v2
    WHERE v2.asset_id = v.asset_id AND v2.column_key = 'col_存放地点1'
  );

-- 2b. 删除待删 key 的所有 EAV 值
DELETE FROM asset_record_value WHERE column_key = 'col_当前存放地点';

-- 2c. 删除待删列定义
DELETE FROM asset_column_def WHERE column_key = 'col_当前存放地点';
```

**Step 3: 在 `AssetSchemaMigrator` 中实现为条件化迁移方法 `ensureColumnDefCleanup()`**，启动时自动检测并执行，记录操作日志。

## 四、实施计划

### Phase 1: 数据库变更 + 数据修复

**`asset_import_batch` 表 DDL**:

```sql
CREATE TABLE IF NOT EXISTS asset_import_batch (
    id VARCHAR(64) PRIMARY KEY,
    file_name VARCHAR(255) NOT NULL,
    imported_by VARCHAR(64),
    imported_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    created_count INT DEFAULT 0,
    updated_count INT DEFAULT 0,

    create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP

```

**`asset_record` 加列 + 索引**:

```sql
-- AssetSchemaMigrator.ensureColumnExists() 模式
ALTER TABLE asset_record ADD COLUMN import_batch_id VARCHAR(64) DEFAULT NULL;
```

## 五、风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 清理重复列时误删数据 | 中 | 高 | 动态发现（LIKE '%存放地点%'）→ 先 INSERT 迁移数据到保留 key → 再 DELETE。在 `ensureColumnDefCleanup()` 中条件化执行，记录日志 |
| 导入匹配从"自动建列"改为"拒绝" → 旧的 Excel 文件无法导入 | 中 | 中 | 导入预览显示被拒绝的列 + 原因 + 建议纠正方案。用户修正 Excel 表头后重新导入 |
| `Promise.all` 并发 200 请求打爆浏览器连接池 | 低 | 中 | 浏览器 HTTP/2 连接复用可承受 200 并发；保守方案用 `p-limit` 限制为 10 并发 |
| 批量删除误操作 | 中 | 高 | 确认对话框显示选中资产列表摘要（前5条 + "等N条"）+ 支持回收站恢复 |
| `import_batch_id` 为 NULL 的历史数据 | 低 | 低 | 历史数据 batch_id=NULL，按批次删除只影响指定 batch_id 的行 |
| 同一资产被两次导入（不同批次）→ `import_batch_id` 被后者覆盖 | 中 | 低 | last-write-wins 策略 — 记录最后一次导入的批次 ID，按批次删除时可能漏删旧批次中的该资产。**可接受**：旧批次中的该资产已被新批次数据覆盖 |
| 批量操作 ID 列表过大导致 SQL 超时 | 低 | 中 | 前端 + 后端双重限制：单次批量操作 ≤ 500 条 |
| `asset_record` 大表加列 + 索引耗时 | 中 | 中 | ALTER TABLE ADD COLUMN 对已有行默认 NULL，通常秒级完成；索引创建视数据量而定 |

| 功能 | 暂缓理由 |

| 自动填充 | 需要实现填充柄 UI + 序列推断算法 |
| 键盘导航 | 需要重构表格为 ARIA grid pattern，与组件拆分并行实施 |
