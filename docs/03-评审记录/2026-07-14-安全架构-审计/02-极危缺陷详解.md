# 02 — 极危缺陷详解（零知识远程接管）

> 6 项。攻击者无需任何凭据即可完全接管任意账户。

---

## NS1. JWT Mock Token 万能后门

**位置**: `JwtTokenService.java:77-86`

```java
private static final String LEGACY_MOCK_PREFIX = "jwt_mock_token_";

public User validateTokenAndResolveUser(String token) {
    if (token.startsWith(LEGACY_MOCK_PREFIX)) {     // ← 检查前缀
        String userId = token.substring(LEGACY_MOCK_PREFIX.length());
        User user = userMapper.findById(userId);     // ← 直接查库，零密码学验证
        if (user == null) return null;
        if (user.getStatus() != null && user.getStatus() == 0) return null;
        return user;                                 // ← 以该用户身份返回
    }
    // ... 下方是正常的 JWT 签名验证（永远不会执行到）
```

**攻击演示**:
```bash
# 以超级管理员身份访问任意受保护端点（单行 curl，零前置知识）
curl -H "Authorization: Bearer jwt_mock_token_SYS_SUPER_ROOT" "https://target/api/admin/users"
```

**影响**: 任何知道或猜到有效 userId 的人可以绕过全部 JWT 签名验证，以该用户身份访问所有 `/api/**` 端点。前端 `authStorage.ts:13` 仍保留 `MOCK_JWT_PREFIX` 常量，`getUserIdFromToken()` 方法（第 133-138 行）依赖此前缀。

**为什么原审计遗漏**: 原审计 S1 仅扫描了 `application.properties` 中的 JWT 密钥配置，未审查 `validateTokenAndResolveUser()` 方法体。该后门位于方法第 1-10 行，独立于任何配置项。

**修复**: 删除第 77-87 行的 `LEGACY_MOCK_PREFIX` 分支、第 119 行的 `isImpersonatedToken()` 中的绕过逻辑。同步删除前端 `authStorage.ts` 中的 `MOCK_JWT_PREFIX` 常量和 `getUserIdFromToken()` 方法。

## NS2. 人脸验证登录完全可绕过 — faceVerified 字段客户端可控

**位置**: `SpecialChannelService.java:84-92`

```java
public AuthData login(String userId, String rawPin, Boolean faceVerified) {
    requirePersonnelExists(userId);                    // ← 只需在人员库中存在

    if (Boolean.TRUE.equals(faceVerified)) {           // ← 客户端 JSON 布尔字段
        failMap.remove(userId);
        ensureAccountExists(userId);                   // ← 自动创建账户
        log.info("[special-channel] face login ok userId={}", userId);
        return generateAuthForUser(userId);            // ← 直接签发 JWT！
    }
    // PIN 验证永远不会执行
```

**关键事实**:
- 端点 `POST /api/auth/special-channel/login` 处于 `/api/auth/**` 排除路径，无任何认证要求
- 服务端**没有任何机制**验证人脸识别是否真实发生
- `faceVerified` 是客户端 JSON 请求体中的普通布尔字段
- `ensureAccountExists()` 在被攻击用户不存在 `sys_user` 记录时会**自动创建**
- 成功登录后获得 **30 天有效期的 JWT Token**

**攻击演示**:
```bash
# 零知识攻击：仅需知道一个学号
curl -X POST "https://target/api/auth/special-channel/login" \
  -H "Content-Type: application/json" \
  -d '{"userId": "STUDENT_2024001", "faceVerified": true}'
# 返回: {"success":true, "data":{"token":"eyJhbGciOiJIUzI1NiJ9...","user":{...}}}
```

**为什么原审计遗漏**: 原审计未审查 `SpecialChannelController` 和 `SpecialChannelService` 的任何代码。

**修复**:
1. 删除 `Boolean faceVerified` 参数，改为要求客户端传入 `faceVerifyToken`
2. 服务端调用 `jwtTokenService.validateFaceVerifyToken(faceVerifyToken, userId)` 验证（该方法已存在，签名见 `JwtTokenService.java:140-160`）
3. 对该端点添加严格的 IP 级别和账号级别限流

## NS5. 密码重置可远程创建任意账户 — 账户注入攻击

**位置**: `AuthController.java:374-396`

原审计 S3 标记了密码重置缺少验证步骤，但遗漏了该端点中的**自动账户创建**功能：

```java
User user = userMapper.findById(userId);
if (user == null) {
    // ⚠️ 自动创建 sys_user！任何在人员库中的人都可以被远程创建账户
    User newUser = new User();
    newUser.setId(userId);
    newUser.setUsername(username);
    newUser.setPassword(hash);          // ← 攻击者设置的密码
    newUser.setRole(RoleEnum.MEMBER);
    newUser.setStatus(1);
    userMapper.insertUser(newUser);
    userMapper.updatePasswordWithPlainById(userId, hash, encryptedPlain, 0);
}
```

**攻击场景**:
1. 获取任意学号（小程序公开可见）
2. 直接调用 `/forgot-password/reset` 设置新密码
3. 系统自动创建 `sys_user` 记录（如果尚未存在）
4. 直接用新密码登录，获取该人员所有数据权限

**修复**:
1. 删除自动创建 `sys_user` 的逻辑（改为返回错误"该账号尚未注册"）
2. 在 `/forgot-password/verify` 成功后生成一次性重置 token
3. `/forgot-password/reset` 强制验证该 token

## NS6. 特殊通道 PIN 设置完全无认证 — 任意账户接管

**位置**: `SpecialChannelController.java:31-45`

所有 `/api/auth/special-channel/**` 端点均无认证（被 `/api/auth/**` 排除规则覆盖）：

```bash
# 步骤 1: 检查目标是否存在（用户枚举）
curl "https://target/api/auth/special-channel/pin-status?userId=STUDENT_X"
# → {"hasPin": false}  ← 用户存在

# 步骤 2: 设置 PIN（无需任何认证）
curl -X POST "https://target/api/auth/special-channel/set-pin" \
  -H "Content-Type: application/json" \
  -d '{"userId": "STUDENT_X", "pin": "123456"}'
# → 返回有效 JWT！攻击者已完全接管该账户
```

**连锁效应**: `set-pin` 成功后直接调用 `generateAuthForUser()` 返回 JWT。攻击者无需知道原密码，无需人脸验证，只需知道学号。

**修复**: PIN 端点添加身份验证（要求携带有效的 faceVerifyToken 或已有的 JWT Token）。

## NS27. /api/admin-nav 完全无认证 — 拦截器路径不匹配极危

| 属性 | 值 |
|------|-----|
| **位置** | `AdminNavConfigController.java:11` + `WebMvcConfig.java:36` |
| **对应标准** | OWASP API5:2023 功能级授权失效 |
| **置信度** | **10/10** |

**根因**：`AdminNavConfigController` 映射到 `@RequestMapping("/api/admin-nav")`，而 `AdminAuthInterceptor` 注册路径为 `addPathPatterns("/api/admin/**")`。Ant 路径模式 `/api/admin/**` **不匹配** `/api/admin-nav`（因为 `**` 只展开路径段，不匹配 `-` 连接的前缀变体）。

**受影响端点**（全部 9 个，零认证）：
```
GET    /api/admin-nav/config          — 返回完整导航配置树
POST   /api/admin-nav/groups          — 创建导航分组
PUT    /api/admin-nav/groups/{id}/move — 移动分组
PUT    /api/admin-nav/groups/{id}     — 更新分组
DELETE /api/admin-nav/groups/{id}     — 删除分组
PUT    /api/admin-nav/items/{id}/move — 移动导航项
PUT    /api/admin-nav/items/reorder   — 重排导航项
POST   /api/admin-nav/ensure-items    — 创建导航项
POST   /api/admin-nav/reset           — 重置全部配置为默认值
```

**攻击演示**：
```bash
# 无需任何认证，直接读取全部导航配置（含所有管理员菜单结构）
curl "https://target/api/admin-nav/config"

# 无需认证，重置导航配置 → 发起 DoS 或注入恶意导航 URL
curl -X POST "https://target/api/admin-nav/reset"
```

**修复**：将 `WebMvcConfig.java:36` 改为 `addPathPatterns("/api/admin/**", "/api/admin-nav/**")`。

## NS28. 扫码终端 7 端点完全无认证暴露公网

| 属性 | 值 |
|------|-----|
| **位置** | `TwinScanController.java` + `TwinApiController.java` |
| **对应标准** | OWASP API1:2023 对象级授权失效 (BOLA) + API2 认证失效 |
| **置信度** | **10/10** |

发现两组完全未认证的端点，涉及敏感 PII 泄露和物理门禁操作：

**组 1: `TwinScanController` — 7 个端点零认证**（设计为内网扫码终端使用，但暴露在公网 `/api/v1/**`）：

| 端点 | 危险操作 | 行号 |
|------|---------|:---:|
| `GET /api/v1/twin/scan/user-status?userId=X` | 读取任意用户 PII + 违规数据 | 495 |
| `POST /api/v1/twin/scan/user-status/update` | 修改任意用户状态 | 502 |
| `GET /api/v1/twin/scan/card-mapping?userId=X` | 读取物理门禁卡号 + 大华序列号 | 517 |
| `POST /api/v1/twin/scan/student-dahua-bind` | 绑定物理卡到任意用户 | 543 |
| `POST /api/v1/twin/scan/clean-exit` | 强制任意用户签离 | 613 |
| `POST /api/v1/twin/scan/violation-interactive-ack` | 替任意用户确认违规 | 156 |
| `POST /api/v1/twin/scan/notice-auto-suppress` | 替任意用户屏蔽弹窗通知 | 190 |

**组 2: `TwinApiController` — 用户敏感数据端点零认证**：

| 端点 | 行号 |
|------|:---:|
| `GET /api/v1/twin/dashboard/user-status?userId=X` | 364 |

**影响**：攻击者可读取全校人员 PII、修改物理门禁卡绑定、绕过违规处理、强制他人签离。这些端点原本应通过内网隔离或扫码终端硬件 Token 保护，但被部署在公网 API 路径下且无任何认证。

**修复**：
1. 为 7 个端点添加 `requireOperator()` 或等效认证
2. 或将这些端点移至独立端口，配合硬件防火墙仅内网可达
3. 短期内至少添加 `ApiAuthInterceptor` 路径覆盖
