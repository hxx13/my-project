# 03 — 阻断级缺陷详解（生产准入阻塞）

> 12 项。必须全部修复才能进入生产环境。

## S1. JWT 密钥硬编码在 git 仓库

**位置**: `application.properties` 第 32 行
```
app.jwt.secret=kjDJOuVmTcsMkqSMs89tgCOfkSvgcKqRiPCsKmd56Zk=
```

**影响**: 任何有仓库读取权限的人都能伪造任意用户（含 SUPER_ADMIN）的 JWT Token。

**修复**:
1. 生成新密钥：`openssl rand -base64 32`
2. 通过环境变量 `JWT_SECRET` 注入，删除配置默认值
3. 从 git 历史中清除：`git filter-branch` 或 `BFG Repo-Cleaner`
4. 轮换后，所有已签发的 Token 立即失效，需用户重新登录

**改动影响**: 小。仅改 1 个配置文件 + 部署环境变量。

## S2. 密码明文可逆加密存储

**位置**: `UserMapper.xml` 第 129-147 行，`sys_user.password_plain` 列

```sql
UPDATE sys_user SET password = #{password}, password_plain = #{passwordPlain}, ...
SELECT password_plain FROM sys_user WHERE id = #{id}
```

**影响**: AES 可逆加密意味着密钥泄露 → 所有用户密码明文暴露。当前 AES 密钥也有硬编码后备值（`twin-default-aes-key-for-password-plain-2026`）。

**调用方**（7 处需要修改）:
- `AdminService.java`: 第 110、188、280、282 行
- `StaffRegistrationService.java`: 第 69 行
- `AuthController.java`: 第 396、409 行
- `StudentRegistrationService.java`: 第 144、194 行

**修复策略**:
1. 新建 SQL 迁移文件：`ALTER TABLE sys_user DROP COLUMN password_plain`
2. 移除 `UserMapper.xml` 中的 `updatePasswordWithPlainById` 和 `getPasswordPlainById`
3. 修改 7 处调用方——原本读取明文密码的逻辑改为"生成随机新密码并通知用户重置"
4. 移除 `AesEncryptionService` 的硬编码后备密钥

**改动影响**: 中。需改 2 个 XML + 4 个 Java 文件（共 7 处），加 1 个 SQL 迁移。功能替代方案需要产品确认（原明文密码用于什么场景？）。

## S3. 密码重置可绕过验证步骤

> **注意**: 该缺陷在补充审计 NS5 中已被升级为 🔴🔴 极危——密码重置端点中发现了**自动创建任意账户**功能。详见 `02-极危缺陷详解.md` § NS5。本节保留 S3 原始描述。

**位置**: `AuthController.java` 第 357-413 行

`POST /api/auth/forgot-password/reset` 不检查用户是否已完成第 1 步的验证。攻击者可：
1. 直接调用 `/forgot-password/reset` 并传入任意 `userId`
2. 绕过手机号验证
3. 重置任意用户密码

**修复**:
- 在 `/forgot-password/verify` 成功后生成一个短命的 HMAC 签名重置 token（含 userId + 过期时间 5 分钟）
- `/forgot-password/reset` 要求验证该 token
- 统一错误消息（不区分"userId 不存在"和"手机号不匹配"）

**改动影响**: 小。修改 1 个 Controller 中 2 个方法。

## S4. 模拟端点缺少 SUPER_ADMIN 角色检查

**位置**: `AuthImpersonationController.java` 第 44-79 行

```java
@PostMapping("/impersonate")
public Result<Map<String, Object>> impersonate(HttpServletRequest request) {
    User user = authContextService.resolveUserFromBearer(request.getHeader("Authorization"));
    if (user == null) {
        return Result.error("未登录或Token无效");
    }
    // ⚠️ 没有任何角色检查！任何有 ARO 绑定的用户都可以模拟他人
```

**修复**: 在生成模拟 token 前加一行：
```java
if (user.getRole().getLevel() < RoleEnum.SUPER_ADMIN.getLevel()) {
    return Result.fail(403, "需要超级管理员权限");
}
```

**改动影响**: 极小。1 行代码。

## S5. 人脸底库无认证 + proxy-image SSRF

**位置**: `FaceBaselineController.java`

- `GET /api/face/baseline/{userId}` — 无任何认证，任何人可查看任意用户的人脸底库
- `GET /api/face/baseline/proxy-image` — 被 `apiAuthInterceptor` 排除，无认证，且接受任意 URL 参数（`URI.create(url).toURL().openStream()`），可被用于 SSRF 攻击（探测内网、访问云元数据端点）

**修复**:
1. 给 `getBaselines()` 加 `requireAdmin()` 或至少 `requireStaff()`
2. `proxyImage()` 加 URL 白名单校验（只允许已知图片 CDN/存储域名）
3. 将 `proxy-image` 从拦截器排除列表中移除，或在其内部加认证

**改动影响**: 小。1 个 Controller 文件。

## S6. 全程 HTTP 明文，nginx 未启用 TLS

**位置**: nginx 生产配置

当前生产 nginx 配置中 SSL/TLS 被注释掉，HTTP→HTTPS 跳转被注释掉。用户密码、JWT Token、人脸底库 全部在公网上明文传输。

**修复**: 已于《反代配置详解》和《进阶升级计划》中完整设计。核心步骤：
1. 启用 SSL 证书（已有 `*.shsmu.edu.cn` 泛域名证书）
2. 开启 HTTP→HTTPS 301 跳转
3. 配置 HSTS 头
4. 前台 80/443 端口对外开放（需学校网络中心配合）

**改动影响**: 小。仅 nginx 配置变更。

## NS3. 云函数代理密钥保护完全未启用 — 安全机制默认关闭

**位置**: `application.properties:88` + `MpCloudProxySecretFilter.java:60-63`

```properties
# application.properties:88 — 密钥为空字符串
app.mp.proxy.secret=
```

```java
// MpCloudProxySecretFilter.java:60-63 — 空密钥 → 全部放行
if (!StringUtils.hasText(expectedSecret)) {
    filterChain.doFilter(request, response);  // ← 不检查任何请求
    return;
}
```

**影响**: 该 Filter 设计意图是要求所有通过云函数代理的 `/api/**` 请求携带 `X-Proxy-Secret` 头。由于密钥未配置，整个外层保护层形同虚设。如果生产环境实际依赖云函数代理，代理和源站之间没有认证。

**修复**: 通过环境变量注入强随机 secret。

## NS4. AES 加密默认密钥已随审计报告公开泄露

**位置**: `AesEncryptionService.java:84-85`

```java
String seed = (configuredKey != null && !configuredKey.isBlank())
        ? configuredKey
        : "twin-default-aes-key-for-password-plain-2026";  // ← 公开的默认密钥
```

**关键事实**:
- `app.password-aes-key` 未在 `application.properties` 中设置 → 始终使用默认后备值
- 该默认密钥已在本文档 S2 部分逐字引用，任何读过本报告的人都知道解密密钥
- 配合 NS1 Mock Token 后门：获取管理员权限 → 调用 `AdminService.viewPassword()` → 用已知 AES 密钥解密 → 全量明文密码泄露

**修复**: 通过环境变量注入独立随机密钥（`openssl rand -base64 32`），删除硬编码后备值，改为启动时抛出异常。

## NS7. Swagger/OpenAPI 无环境限制 — 完整 API 蓝图公开暴露

**位置**: `OpenApiConfig.java`

`OpenApiConfig` 类无 `@Profile` 注解，在所有环境生效。`application.properties` 中未设置 `springdoc.api-docs.enabled=false`。这意味着 `/v3/api-docs` 和 `/swagger-ui.html` 在生产环境公开可访问。攻击者可以获得完整的 API 端点清单、请求/响应 schema、认证方案。

**修复**: 添加 `@Profile("!prod")`。

## NS12. 存储型 XSS — 通知内容未经 HTML 转义即渲染

| 属性 | 值 |
|------|-----|
| **位置** | `NotificationService.java:208` → `student-notifications.tsx:274` → 全链路 |
| **对应标准** | OWASP A03 注入 / CWE-79 存储型 XSS |
| **置信度** | **9/10** |

**服务端**（`NotificationService.java:208`）：
```java
item.put("contentHtml", StringUtils.hasText(content) ? "<p>" + content + "</p>" : "");
// ⚠️ content 来自数据库，直接拼入 HTML 标签，未经任何 HTML 实体编码
```

**客户端**（`student-notifications.tsx:274`）：
```tsx
<div
  className="rich-text-content"
  dangerouslySetInnerHTML={{ __html: selectedNotification.content || selectedNotification.summary }}
/>
// ⚠️ 未经过 DOMPurify 消毒，直接渲染为 HTML
```

**攻击链路**：
1. 管理员通过通知系统创建包含恶意脚本的通知内容
2. 内容原样存入 `sys_student_notification.content` 列
3. 服务端读取后用 `<p>` 包裹为 `contentHtml`，不做转义
4. 前端 `dangerouslySetInnerHTML` 直接渲染为 DOM
5. 学生打开通知弹窗 → 脚本在其浏览器中以同源上下文执行

**影响**：若攻击者获得管理员权限（如 NS1 mock token），可向所有学生推送含 XSS 的通知。脚本可窃取学生 JWT Token（存于 localStorage）、发起 API 请求、修改学生数据。攻击面覆盖整个学生用户群。

**修复**：
1. **服务端**（首选）：`NotificationService.java:208` 使用 `StringEscapeUtils.escapeHtml4(content)` 转义
2. **客户端**（纵深防御）：`student-notifications.tsx:274` 添加 `DOMPurify.sanitize()` 包裹
3. **全量排查**：所有 `dangerouslySetInnerHTML` 使用点（已统计 8 处）逐一确认有 DOMPurify 或等效消毒

**同类风险文件**（需逐一核验 DOMPurify 覆盖）：
- `MobileFeedbackPanel.tsx:133` — `item.contentHtml` 直接渲染
- `MobileViolationsTab.tsx:161-162` — `prepareMobileNoticeHtml()` 但无消毒
- `ChatMarkdownBody.tsx:24` — Markdown 渲染（已通过 `renderMarkdownToSafeHtml` + DOMPurify）
- `RichTextHtmlBody.tsx:27` — 富文本（已通过 `sanitizeRichTextHtml` + DOMPurify）
- `ViolationBoardRow.tsx:96` — 已通过 DOMPurify ✅

## NS13. BCrypt 密码哈希在管理员 API 响应中泄露

| 属性 | 值 |
|------|-----|
| **位置** | `AdminMapper.xml:15,57` → `AdminController.java:38-58` |
| **对应标准** | OWASP A02 加密失败 / CWE-522 凭据不足的防护 |
| **置信度** | **10/10** |

**服务端**（`AdminMapper.xml`）：
```sql
-- getPersonnelWithAuth (line 15):
SELECT ... su.password, ... FROM sys_user su ...

-- getSystemOnlyUsers (line 57):  
SELECT ... su.password, ... FROM sys_user su ...
```

两个查询均显式 SELECT `su.password`（BCrypt 哈希），数据经 `AdminService.listPersonnel()` / `listSystemUsers()` → `AdminController` 原样返回 JSON。

**影响**：
- 任何具有 STAFF 及以上角色的用户调用 `/api/admin/users/**` 即可获取所有用户的 BCrypt 哈希
- BCrypt 哈希虽然不可逆，但泄露后可在离线环境被暴力破解
- 配合 NS1 mock token 后门：匿名攻击者可直接获取全量密码哈希
- 违反最小数据暴露原则：密码哈希**绝不应离开数据库**

**修复**：
1. `AdminMapper.xml` 两个查询中移除 `su.password` 列
2. 若前端确实需要密码相关字段，添加 `passwordSet` 布尔字段（`CASE WHEN su.password IS NOT NULL THEN 1 ELSE 0 END`）代替
3. 全量审查所有 Mapper XML：确认无其他 SELECT 包含 `password`、`password_plain`、`secret` 等敏感列

## NS14. JWT 令牌无吊销机制 — 泄露即永久有效

| 属性 | 值 |
|------|-----|
| **位置** | `JwtTokenService.java` 全类 |
| **对应标准** | NIST SP 800-63B §4.1.4 令牌管理 / OWASP ASVS V2.2.3 |
| **置信度** | **9/10** |

**事实**：
- JWT 签发后 30 天有效（`JwtTokenService.java:57`），可刷新至 60 天（`JwtTokenService.java:176-177`）
- **无任何黑名单、吊销列表或令牌失效机制**
- 密码修改不清除已有 JWT（用户改密后旧 Token 仍有效）
- 角色变更不清除已有 JWT（权限降级后旧 Token 仍保留原角色）
- 用户禁用不清除已有 JWT（仅检查 `status != 0`，可在下一次请求时拦截，但已颁发的模拟 Token 不受影响）

**攻击场景**：
1. Token 通过 XSS、日志泄露、中间人攻击被窃取
2. 用户发现异常后修改密码 → 攻击者的旧 Token **仍然有效长达 30 天**
3. 用户被管理员降权 → 旧 Token 仍然保留原高权限角色（角色编码在 JWT claims 中）

**修复**：
1. **短期**：在 `sys_user` 表添加 `token_version` 列，JWT claims 中包含此版本号，验证时比对。密码修改/角色变更/管理员强制下线时递增版本号 → 所有旧 Token 立即失效
2. **中期**：实现 Redis 黑名单，关键操作（密码修改、角色变更）时将被吊销 Token 的 jti 加入黑名单（TTL = Token 剩余有效期）
3. **长期**：迁移至 OAuth 2.0 / OpenID Connect 会话管理体系
