# 05 — 中低优缺陷详解

> 19 项中优 + 2 项低优。不阻塞生产准入，但应在首次部署后分批修复。

## 🟡 中优先级（19项）

### S13. 196 @Autowired 字段注入 + 10 @Lazy 循环依赖

**风险等级**: 🟡 中 | **位置**: 44 个文件

**度量**: 196 个 `@Autowired` 字段注入点、10 个 `@Lazy` 逃生舱口。最严重文件：`TwinScanAppService.java`（18 注入点）、`AroSyncTask.java`（16 注入点 + 1 @Lazy）、`TwinScanService.java`（12 注入点）、`ScanDelayRequestService.java`（12 注入点 + 1 @Lazy）。

**影响**: 字段注入隐藏依赖图，无法从类签名看出其依赖结构。`@Lazy` 是循环依赖的信号——类之间互相引用，Spring 无法决定创建顺序，导致启动顺序不确定。测试时必须启动完整 Spring 上下文才能注入 Mock。`@Lazy` 代理在完成前被调用有 NPE 风险。

**修复**: 将字段注入改为构造函数注入。约 44 个文件，每个 5-10 分钟，合计约 1 人天。这是机械性重构——改 `@Autowired private X x` 为构造函数参数。

### S14. 33 Controller 直接调 Mapper

**风险等级**: 🟡 中 | **位置**: 33 个 Controller 类

**数据**: 33 个 Controller 绕过 Service 层直接操作 Mapper。最大违规者：`StudentMobileCenterController.java`（861 行，直接使用 6 个 Mapper）、`MonitorController.java`（902 行，直接使用 `TwinAutomationLogMapper`）。

**影响**: 业务逻辑和 SQL 查询混在 Controller 中，无法单独测试、无法复用、无法做事务管理。Controller 层承担了过多的职责，违反单一职责原则。

**修复**: 每对 Mapper 调用需要提取到对应 Service 中。可以渐进式做——每次改一个 Controller-Mapper 对，不需要一次性完成全部 33 个。

### S15. 36 God Service 超过 500 行

**风险等级**: 🟡 中 | **位置**: 36 个 Service 类

| Service | 行数 | 可能拆分方向 |
|---------|:---:|------|
| `MaterialService` | 1,930 | CRUD / 审批工作流 / 通知 / ARO 集成 |
| `AssetService` | 1,885 | CRUD / 折旧计算 / 盘点 / 报表 |
| `FacilityMaintenanceService` | 1,600 | 报修 / 派单 / 完工 / 评价 |
| `SuppliesService` | 1,595 | 申领 / 审批 / 库存 / 采购 |
| `AccessSwingCleanWorkspaceService` | 1,590 | — |

**影响**: 单体 Service 承担过多职责，修改困难、测试困难、合并冲突频繁。每个 God Service 内部隐含了多个子域，但没有明确的边界。

**修复**: 拆分为 3-5 个聚焦 Service。需要理解现有业务逻辑，不能机械拆分——必须确定每个方法属于哪个子域。建议在项目空闲期分批次做，每次拆 1 个 God Service。

### S16. twin 模块 15 路辐射依赖

**风险等级**: 🟡 中 | **位置**: `twin` 模块 + `me` 模块

**数据**: `twin` 模块被其他 15 个模块引用，形成中心辐射型依赖图。`me` 模块（个人中心）也引用了 12 个其他模块。

**影响**: 修改 `twin` 模块的接口影响 15 个消费方。模块间耦合度极高，任何变更都需要大范围回归测试。

**修复**: 需要引入事件总线或应用服务层解耦。这是架构级别的重设计，不应在安全修复阶段做。需专门立项。

### S17. SQL 拼接风险

**风险等级**: 🟡 中 | **位置**: 1 处（Mapper XML 或 Java 拼接点）

**描述**: 代码库中存在未使用参数化查询 `#{}` 的 SQL 拼接点。虽然大部分 MyBatis Mapper 正确使用了 `#{}` 绑定，但个别位置使用了 `${}` 字符串拼接或 Java 代码中拼接 SQL 片段。

**影响**: `${}` 拼接直接将参数值嵌入 SQL 语句，若参数来自用户输入则存在 SQL 注入风险。即使当前参数来自内部系统，未来业务变更可能引入外部输入。

**修复**: 将 `${}` 改为 `#{}` 参数化查询。改动影响：小，仅 1 处修改，约 15 分钟。

---

### S18. 文件上传主通道无类型白名单 + 路径穿越不一致 🟡→🟠

**风险等级**: 🟡→🟠 中→高 | **位置**: `UploadController.java`

**描述**: 文件上传的主入口缺少文件扩展名白名单校验，攻击者可上传任意类型文件（包括可执行脚本）。同时路径穿越防护在多个上传方法中实现不一致——部分方法有 `normalize()` + `startsWith()` 完整校验，部分缺失。

**影响**: 上传 webshell、恶意脚本、或通过路径穿越覆盖系统文件。虽然 nginx 可能限制了上传目录的执行权限，但应用层不应依赖基础设施层的防护。

**修复**: 添加文件扩展名白名单（仅允许图片、文档、压缩包等安全类型）+ 统一所有上传路径的路径穿越校验。改动影响：小。1 个 Service 添加校验方法，约 30 分钟。

---

### S19. 配置管理 290 行单片文件

**风险等级**: 🟡 中 | **位置**: 配置文件

**描述**: 项目配置文件（`application.properties` 或等效配置类）达 290 行，所有模块的配置混在一个文件中。缺乏按环境（dev/test/prod）的 profile 分离。

**影响**: 配置混乱增加误改风险——修改某模块配置时可能意外影响其他模块。缺乏 profile 分离导致生产/测试环境差异不明确，易发生"测试通过、生产炸"的问题。配置文件中敏感值（密码、密钥）与非敏感配置混杂，增加泄露面。

**修复**: 按模块拆分配置文件（`application-db.properties`、`application-thirdparty.properties` 等），创建 `application-prod.properties` 将敏感值外置为环境变量占位符。改动影响：中。配置文件拆分 + 部署文档更新，约半天。

### S20. 多处限流端点缺失

**风险等级**: 🟡 中 | **位置**: `AuthEndpointRateLimitFilter` 配置范围

**描述**: 当前 `AuthEndpointRateLimitFilter` 仅覆盖认证相关端点（登录、密码重置等），大量非认证端点的 API 缺少速率限制。此外，Filter 本身存在 S12（X-Forwarded-For 可伪造）的 IP 识别问题。

**影响**: 攻击者可对未限流端点发起高频调用：数据导出端点被刷导致服务器负载飙升、批量查询端点被用于枚举数据。虽然现有 Filter 覆盖了认证链路，但其他业务端点面临资源耗尽风险。

**修复**: 扩展 `AuthEndpointRateLimitFilter` 的路径覆盖范围（或创建通用 `RateLimitFilter`），对所有 API 端点配置合理的速率限制。同时修复 S12 的 IP 获取逻辑（取 `X-Forwarded-For` 最右侧或 `remoteAddr`）。改动影响：小。补 Filter 配置，约 1 小时。

---

### NS20. PII (userId + IP) 在 INFO 级别日志中暴露

**风险等级**: 🟡 中 | **位置**: 多处

**对应标准**: GDPR Art.5(1)(c) 数据最小化 / PIPL 个人信息保护法

**描述**: 多个 Service 和 Controller 在 INFO 日志级别记录了包含 userId 和 IP 地址的日志：

```java
// StudentMobileTokenService.java:72
log.info("Mobile token first access: userId={}, ip={}", record.getUserId(), ip);

// SpecialChannelService.java:72
log.info("[special-channel] PIN set userId={}", userId);

// StudentMobileCenterController.java:772
log.info("User {} generated mobile token for userId={}, expiresAt={}", currentUser.getId(), userId, expiresAt);
```

**影响**: userId + IP 组合在 PIPL/GDPR 下属于个人信息。生产环境 INFO 日志通常被集中采集并长期留存（ELK/Splunk/云日志服务），构成隐私合规风险。若日志系统被入侵或运维人员未授权查看，构成个人信息泄露。

**修复**: 生产环境将敏感操作的日志级别降为 DEBUG，或对 userId 做哈希化处理后记录（`Hashing.sha256(userId).substring(0, 8)`）。改动影响：小。调整日志级别或添加脱敏工具方法，约 1 小时。

---

### NS21. Cookie 安全属性全面缺失

**风险等级**: 🟡 中 | **位置**: 全局

**对应标准**: OWASP ASVS V3.4

**描述**: 当前系统基本不依赖 Cookie（使用 Bearer Token + localStorage），但 `JSESSIONID` 等 Servlet 容器自动生成的 Cookie 仍然存在。检查发现：无 `HttpOnly` 设置（JavaScript 可读取），无 `Secure` 标志（HTTP 连接也会发送），无 `SameSite` 属性（跨站请求会附带），无 Cookie Prefix（`__Host-`）。

**影响**: 虽然 `JSESSIONID` 未被业务代码使用，但其存在本身仍有风险——攻击者可通过 MITM 窃取、通过 XSS 读取（缺少 HttpOnly）、被跨站请求携带（缺少 SameSite）。

**修复**: 在 `application.properties` 中添加：
```properties
server.servlet.session.cookie.http-only=true
server.servlet.session.cookie.secure=true
server.servlet.session.cookie.same-site=strict
```
改动影响：极小。3 行配置，约 15 分钟。

### NS22. JWT 角色陈旧 — 权限变更后 Token 中角色不更新

**风险等级**: 🟡 中 | **位置**: `JwtTokenService.java:55,66`

**对应标准**: OWASP ASVS V2.2.5

**描述**: JWT 签发时将 `role` 编码于 claims 中（`generateToken` 第 55 行、`generateImpersonationToken` 第 66 行）。验证时**信任 claims 中的角色**，不重新从数据库读取当前角色。

**影响**: 管理员在后台将某用户从 STAFF 降级为 MEMBER，该用户已有 Token 仍以 STAFF 身份访问。Token 最长存活 30 天，权限降级最多延迟 30 天才生效。结合 NS14（无吊销机制），问题加剧——管理员无法强制某一用户的权限变更立即生效。

**修复**: 在 `AdminAuthInterceptor` 和 `ApiAuthInterceptor` 中验证 Token 后重新从数据库加载用户角色（而非信任 JWT claims），或结合 NS14 的 `token_version` 机制——角色变更时递增版本号使旧 Token 立即失效。改动影响：小。Interceptor 中添加角色重查逻辑，约 2 小时。

---

### NS23. 遗留调试/管理端点暴露

**风险等级**: 🟡 中 | **位置**: 全局

**对应标准**: OWASP API9:2023 资产清单不当

**描述**: 发现多个遗留或调试端点未添加环境限制或角色检查：

| 端点 | 位置 | 风险 |
|------|------|------|
| `/api/v1/twin/rpg/**` | `RpgController.java` | 批量重算/同步，无角色检查 |
| `/api/v1/twin/prediction/admin/trigger` | `TwinPredictionController.java` | 触发模型重算，无角色检查 |
| `/api/v1/twin/dashboard/debug/**` | `TwinApiController.java` | 调试端点，详见 NS29 |
| `/api/v1/monitor/**` | 排除在 `requestMetricsInterceptor` 外 | 监控端点暴露 |

**影响**: 这些端点原本可能设计为内部运维使用，但被部署在公网 API 路径下且无认证或仅有基础认证。未授权触发大批量同步/重算任务可能造成 DoS（服务器过载）或数据一致性问题。

**修复**: 为调试/管理类端点添加 `@Profile("!prod")`（生产环境完全禁用），或添加 SUPER_ADMIN 角色检查（需登录管理员才能调用）。改动影响：小。约 1 小时。

### NS24. 无账号级登录失败防护（撞库/凭证填充）

**风险等级**: 🟡 中 | **位置**: `AuthController.java` 登录端点

**对应标准**: NIST SP 800-63B §5.2.2

**描述**: 当前登录端点**无账号级别失败计数**（某个用户连续尝试密码多少次后锁定）、无验证码机制（CAPTCHA）、无渐进式延迟（连续失败后等待时间递增）。唯一防护是 `AuthEndpointRateLimitFilter` 的 IP 级别限流，但该 Filter 存在 S12（X-Forwarded-For 可伪造）问题。

**影响**: 攻击者伪造 IP 绕过 IP 限流后，可对特定账号发起无限次密码尝试（撞库）。若使用弱密码的用户存在，攻击者可通过词典攻击成功登录。结合 NS1（mock token），攻击者甚至无需破解密码。

**修复**: 引入账号级别登录失败计数：连续 3 次失败后锁定账号 15 分钟，或要求输入验证码（引入图形验证码或短信验证码）。结合 `AuthEndpointRateLimitFilter` IP 限流形成纵深防护。改动影响：小。`AuthController` 和 `UserService` 添加失败计数逻辑，约 2 小时。

### NS25. 通知内容服务端未做 HTML 编码

**风险等级**: 🟡 中 | **位置**: `NotificationService.java:208`

**对应标准**: CWE-116 输入编码不当

**描述**: `NotificationService.java:208` 构建 `contentHtml` 时，仅将 `content` 包裹在 `<p>` 标签中，**未调用任何 HTML 实体编码**。这是 NS12 存储型 XSS 的**服务端根因**：

```java
// 当前代码（不安全）
item.put("contentHtml", StringUtils.hasText(content) ? "<p>" + content + "</p>" : "");

// 应改为
item.put("contentHtml", StringUtils.hasText(content)
    ? "<p>" + HtmlUtils.htmlEscape(content) + "</p>"
    : "");
```

（Spring Framework 已内置 `org.springframework.web.util.HtmlUtils.htmlEscape()`。）

**影响**: 若通知内容中包含 HTML 特殊字符（`<script>`、`<img onerror=>` 等），这些字符将原样嵌入 HTML 并被浏览器解析为 DOM 元素/事件处理器。这是 XSS 的经典攻击向量。

**修复**: 服务端使用 `HtmlUtils.htmlEscape(content)` 对所有用户可控内容进行 HTML 实体编码。客户端 `dangerouslySetInnerHTML` 使用点添加 DOMPurify 作为纵深防御。改动影响：极小。1 行代码，约 30 分钟。

### NS26. 密码重置/PIN 设置多步操作无状态机完整性

**风险等级**: 🟡 中 | **位置**: `AuthController.java`, `SpecialChannelController.java`

**对应标准**: OWASP ASVS V4.1 业务逻辑

**描述**: 忘记密码流程（verify → reset）和 PIN 设置流程均为**无状态**操作，各步骤之间无：

- 服务端签发的临时令牌以绑定步骤
- 步骤顺序强制校验（攻击者可跳过 verify 直接调 reset）
- 时效性限制（verify 完成后无时间窗口约束）

**影响**: 详见 S3（密码重置可绕过验证步骤）和 NS6（PIN 设置无认证）。无状态设计使得多步安全流程形同虚设——攻击者可以跳过验证步骤直接执行最终操作。

**修复**: 为需要多步验证的流程引入服务端状态：
1. 步骤 1 成功后签发短命 token（含 userId + 过期时间 + HMAC 签名）
2. 步骤 2 强制校验该 token 的有效性和时效性
3. token 使用后立即作废（防重放）

改动影响: 修复方案已包含在 S3 和 NS6 的修复中。

### NS33. 全项目零 @Min / @Positive / @NotNull 校验注解

**风险等级**: 🟡 中 | **位置**: 全部 DTO 类

**对应标准**: OWASP ASVS V5.1 输入校验

**描述**: 全项目**零个** Jakarta Validation 注解（`@NotNull` / `@NotBlank` / `@Min` / `@Positive` / `@Size`）。这意味着客户端可以发送任意值：

- 采购数量可传 `-1`、`0`、`Integer.MAX_VALUE`（负数采购、零采购、溢出）
- 库存可设为负数
- 价格可传任意值（负数退钱、天文数字）
- 所有必填字段可传空字符串或 null

**影响**: 这是设计层面的"定时炸弹"。当前业务逻辑可能通过其他方式的校验避免了问题，但缺乏统一的输入校验层意味着：新开发者可能遗漏校验、现有代码路径可能被非预期输入触发异常、恶意客户端可通过边界值攻击诱发逻辑错误。

**修复**: 对所有 DTO 的数值/必填字段添加 Jakarta Validation 注解，Controller 相应方法添加 `@Valid` 触发校验。改造可渐进式——优先覆盖涉及金额、库存、权限的关键 DTO。改动影响：大（全量 DTO），可分批推进，约 2 天。

### NS34. MySQL + WinCC + Dahua 均禁用 TLS

**风险等级**: 🟡 中 | **位置**: `application.properties:60,158,225`

**对应标准**: OWASP A02 加密失败 / OWASP ASVS V9.2 传输层安全

**描述**: 三处关键外部连接均禁用了 TLS 加密：

- `useSSL=false` — MySQL 数据库连接凭证明文传输，查询结果明文传输
- `app.wincc.ssl-insecure=true` — WinCC 楼宇自动化系统 TLS 验证禁用
- `app.dahua.ssl-insecure=true` — 大华门禁系统 TLS 验证禁用

**影响**: 门禁系统控制物理门锁开关，TLS 禁用意味着中间人攻击者可劫持门控指令——在内网中，ARP 欺骗即可拦截和篡改门禁开锁命令。WinCC 楼宇系统涉及设备控制和数据采集，明文传输可被篡改控制指令。MySQL 明文传输使数据库凭据和查询结果在网络上裸奔。

**修复**:

1. MySQL：启用 `useSSL=true`，配置 CA 证书验证（即使自签也比禁用强）
2. WinCC/Dahua：配置正确的 TLS 证书，移除 `ssl-insecure=true`。如设备不支持 TLS，至少在应用和设备之间部署加密隧道（如 stunnel）
3. 评估是否可将这些敏感连接隔离到独立 VLAN

改动影响：小。配置变更 + 证书部署，约 1 小时。

### NS35. GDPR/PIPL 合规 — 无自助账户删除/数据导出/同意追踪

**风险等级**: 🟡 中 | **位置**: 全局

**对应标准**: GDPR Art.5/7/17/20 / PIPL 个人信息保护法

**描述**: 系统缺失以下数据主体权利功能：

- **无用户自助删除账户功能**：仅有 SUPER_ADMIN 可删除用户（违反 GDPR Art.17 删除权 / PIPL 第 47 条）
- **无数据导出/便携性**：用户无法导出自己的数据（违反 GDPR Art.20 数据可携带权）
- **无用户同意追踪**：不清楚用户何时/如何同意了隐私政策（违反 GDPR Art.7 同意条件）
- **身份证号未脱敏**：`AroPersonnel` DTO 包含完整身份证号（`idNumber`），API 响应中直接暴露

**影响**: 在中国境内运营涉及大量学生个人信息（含身份证号），PIPL 合规要求：提供数据删除、数据导出、同意管理功能。GDPR 合规取决于系统是否处理欧盟居民数据（当前可能不涉及，但建议按 GDPR 标准设计以减少未来合规成本）。

**修复**:

1. 添加用户自助账户删除入口（前端页面 + 后端端点），删除前验证身份（密码二次确认）
2. 添加数据导出功能（JSON/CSV 格式，涵盖用户在该系统内的全部个人数据）
3. 在用户注册/首次登录时记录同意时间戳和隐私政策版本号

### S22. Spring Boot 3.5.11-SNAPSHOT 使用快照版本

**风险等级**: 🟢 低 | **位置**: `pom.xml` — `spring-boot-starter-parent` 版本
