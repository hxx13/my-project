> **审计日期**: 2026-07-14 | **审计方式**: 4 个独立 Agent 并行探索（配置/架构层）+ 逐行源码审查 + 攻击链路推演（代码逻辑层）+ 4 路专项代理攻击面探索（IDOR/Mass Assignment/XSS/认证缺口）+ OWASP 全量标准对齐
> **审计范围**: `src/main/java` + `src/main/resources` + `frontend/src` + nginx 配置 + pom.xml
> **生产准入结论**: ⚠️ **当前不可进入生产环境**，存在 6 个极危零知识接管缺陷、12 个阻断级安全缺陷（其中 4 个涉及物理门禁安全）

## 二-A、补充审计：代码逻辑层阻断漏洞（原审计完全遗漏）

> 原审计（S1-S22）覆盖了配置扫描和架构分析，但在**代码逻辑审查**层面存在显著盲区。以下 7 个漏洞无法通过 grep/SAST 配置扫描发现，需要逐行审查认证流程、条件分支和安全决策点。

### NS1. JWT 遗留 Mock Token 万能后门 🔴🔴 极危

**位置**: `JwtTokenService.java:77-86`

```java
private static final String LEGACY_MOCK_PREFIX = "jwt_mock_token_";

public User validateTokenAndResolveUser(String token) {
    if (token.startsWith(LEGACY_MOCK_PREFIX)) {     // ← 检查前缀
        String userId = token.substring(LEGACY_MOCK_PREFIX.length());
        User user = userMapper.findById(userId);     // ← 直接查库，零密码学验证
        if (user == null) return null;
        if (user.getStatus() != null && user.getStatus() == 0) return null;
        return user;                                 // ← 以该用户身份返回
    }
    // ... 下方是正常的 JWT 签名验证（永远不会执行到）
```

**攻击演示**:
```bash
# 以超级管理员身份访问任意受保护端点（单行 curl，零前置知识）
curl -H "Authorization: Bearer jwt_mock_token_SYS_SUPER_ROOT" "https://target/api/admin/users"
```

**影响**: 任何知道或猜到有效 userId 的人可以绕过全部 JWT 签名验证，以该用户身份访问所有 `/api/**` 端点。前端 `authStorage.ts:13` 仍保留 `MOCK_JWT_PREFIX` 常量，`getUserIdFromToken()` 方法（第 133-138 行）依赖此前缀。

**为什么原审计遗漏**: 原审计 S1 仅扫描了 `application.properties` 中的 JWT 密钥配置，未审查 `validateTokenAndResolveUser()` 方法体。该后门位于方法第 1-10 行，独立于任何配置项。

**修复**: 删除第 77-87 行的 `LEGACY_MOCK_PREFIX` 分支、第 119 行的 `isImpersonatedToken()` 中的绕过逻辑。同步删除前端 `authStorage.ts` 中的 `MOCK_JWT_PREFIX` 常量和 `getUserIdFromToken()` 方法。

### NS2. 人脸验证登录完全可绕过 — faceVerified 字段客户端可控 🔴🔴 极危

**位置**: `SpecialChannelService.java:84-92`

```java
public AuthData login(String userId, String rawPin, Boolean faceVerified) {
    requirePersonnelExists(userId);                    // ← 只需在人员库中存在

    if (Boolean.TRUE.equals(faceVerified)) {           // ← 客户端 JSON 布尔字段
        failMap.remove(userId);
        ensureAccountExists(userId);                   // ← 自动创建账户
        log.info("[special-channel] face login ok userId={}", userId);
        return generateAuthForUser(userId);            // ← 直接签发 JWT！
    }
    // PIN 验证永远不会执行
```

**关键事实**:
- 端点 `POST /api/auth/special-channel/login` 处于 `/api/auth/**` 排除路径，无任何认证要求
- 服务端**没有任何机制**验证人脸识别是否真实发生
- `faceVerified` 是客户端 JSON 请求体中的普通布尔字段
- `ensureAccountExists()` 在被攻击用户不存在 `sys_user` 记录时会**自动创建**
- 成功登录后获得 **30 天有效期的 JWT Token**

**攻击演示**:
```bash
# 零知识攻击：仅需知道一个学号
curl -X POST "https://target/api/auth/special-channel/login" \
  -H "Content-Type: application/json" \
  -d '{"userId": "STUDENT_2024001", "faceVerified": true}'
# 返回: {"success":true, "data":{"token":"eyJhbGciOiJIUzI1NiJ9...","user":{...}}}
```

**为什么原审计遗漏**: 原审计未审查 `SpecialChannelController` 和 `SpecialChannelService` 的任何代码。

**修复**:
1. 删除 `Boolean faceVerified` 参数，改为要求客户端传入 `faceVerifyToken`
2. 服务端调用 `jwtTokenService.validateFaceVerifyToken(faceVerifyToken, userId)` 验证（该方法已存在，签名见 `JwtTokenService.java:140-160`）
3. 对该端点添加严格的 IP 级别和账号级别限流

**位置**: `application.properties:88` + `MpCloudProxySecretFilter.java:60-63`

```properties
# application.properties:88 — 密钥为空字符串
app.mp.proxy.secret=
```

```java
// MpCloudProxySecretFilter.java:60-63 — 空密钥 → 全部放行
if (!StringUtils.hasText(expectedSecret)) {
```

**修复**: 通过环境变量注入强随机 secret。

### NS4. AES 加密默认密钥已随审计报告公开泄露 🔴 阻断

**位置**: `AesEncryptionService.java:84-85`

```java
String seed = (configuredKey != null && !configuredKey.isBlank())
        ? configuredKey
        : "twin-default-aes-key-for-password-plain-2026";  // ← 公开的默认密钥
```

**关键事实**:

### NS5. 密码重置可远程创建任意账户 — 账户注入攻击 🔴🔴 极危

**位置**: `AuthController.java:374-396`

原审计 S3 标记了密码重置缺少验证步骤，但遗漏了该端点中的**自动账户创建**功能：

```java
User user = userMapper.findById(userId);
if (user == null) {
    // ⚠️ 自动创建 sys_user！任何在人员库中的人都可以被远程创建账户
    User newUser = new User();
    newUser.setId(userId);
    newUser.setUsername(username);
    newUser.setPassword(hash);          // ← 攻击者设置的密码
    newUser.setRole(RoleEnum.MEMBER);
    newUser.setStatus(1);
    userMapper.insertUser(newUser);
    userMapper.updatePasswordWithPlainById(userId, hash, encryptedPlain, 0);
}
```

**攻击场景**:
1. 获取任意学号（小程序公开可见）
2. 直接调用 `/forgot-password/reset` 设置新密码
3. 系统自动创建 `sys_user` 记录（如果尚未存在）
4. 直接用新密码登录，获取该人员所有数据权限

**修复**:
1. 删除自动创建 `sys_user` 的逻辑（改为返回错误"该账号尚未注册"）
2. 在 `/forgot-password/verify` 成功后生成一次性重置 token
3. `/forgot-password/reset` 强制验证该 token

### NS6. 特殊通道 PIN 设置完全无认证 — 任意账户接管 🔴🔴 极危

**位置**: `SpecialChannelController.java:31-45`

所有 `/api/auth/special-channel/**` 端点均无认证（被 `/api/auth/**` 排除规则覆盖）：

## 二-B、阻断级缺陷详解（原审计 S1-S6，必须修复才能进入生产）

### S1. JWT 密钥硬编码在 git 仓库

**位置**: `application.properties` 第 32 行
```
app.jwt.secret=kjDJOuVmTcsMkqSMs89tgCOfkSvgcKqRiPCsKmd56Zk=
```

**影响**: 任何有仓库读取权限的人都能伪造任意用户（含 SUPER_ADMIN）的 JWT Token。

**修复**:
1. 生成新密钥：`openssl rand -base64 32`
2. 通过环境变量 `JWT_SECRET` 注入，删除配置默认值
3. 从 git 历史中清除：`git filter-branch` 或 `BFG Repo-Cleaner`
4. 轮换后，所有已签发的 Token 立即失效，需用户重新登录

**改动影响**: 小。仅改 1 个配置文件 + 部署环境变量。

### S2. 密码明文可逆加密存储

**位置**: `UserMapper.xml` 第 129-147 行，`sys_user.password_plain` 列

```sql
UPDATE sys_user SET password = #{password}, password_plain = #{passwordPlain}, ...
SELECT password_plain FROM sys_user WHERE id = #{id}
```

**影响**: AES 可逆加密意味着密钥泄露 → 所有用户密码明文暴露。当前 AES 密钥也有硬编码后备值（`twin-default-aes-key-for-password-plain-2026`）。

**调用方**（7 处需要修改）:
- `AdminService.java`: 第 110、188、280、282 行
- `StaffRegistrationService.java`: 第 69 行
- `AuthController.java`: 第 396、409 行
- `StudentRegistrationService.java`: 第 144、194 行

**修复策略**:
1. 新建 SQL 迁移文件：`ALTER TABLE sys_user DROP COLUMN password_plain`
2. 移除 `UserMapper.xml` 中的 `updatePasswordWithPlainById` 和 `getPasswordPlainById`
3. 修改 7 处调用方——原本读取明文密码的逻辑改为"生成随机新密码并通知用户重置"
4. 移除 `AesEncryptionService` 的硬编码后备密钥

**改动影响**: 中。需改 2 个 XML + 4 个 Java 文件（共 7 处），加 1 个 SQL 迁移。功能替代方案需要产品确认（原明文密码用于什么场景？）。

### S3. 密码重置可绕过验证步骤

**位置**: `AuthController.java` 第 357-413 行

`POST /api/auth/forgot-password/reset` 不检查用户是否已完成第 1 步的验证。攻击者可：
1. 直接调用 `/forgot-password/reset` 并传入任意 `userId`
2. 绕过手机号验证
3. 重置任意用户密码

**修复**:
- 在 `/forgot-password/verify` 成功后生成一个短命的 HMAC 签名重置 token（含 userId + 过期时间 5 分钟）
- `/forgot-password/reset` 要求验证该 token
- 统一错误消息（不区分"userId 不存在"和"手机号不匹配"）

**改动影响**: 小。修改 1 个 Controller 中 2 个方法。

## 四、架构缺陷详解

### S13. 196 @Autowired 字段注入 + 10 @Lazy 循环依赖 🔴

**度量**: 44 个文件、196 个注入点、10 个 `@Lazy` 逃生舱口。

| 最严重文件 | @Autowired 数量 | @Lazy |
|-----------|:---:|:---:|
| `TwinScanAppService.java` | 18 | — |
| `AroSyncTask.java` | 16 | 1 |
| `TwinScanService.java` | 12 | — |
| `ScanDelayRequestService.java` | 12 | 1 |
| `MaterialService.java` (1930行) | — | 1 |

**为什么这是安全问题**: 字段注入隐藏依赖图。你无法从类签名看出它依赖什么。`@Lazy` 是循环依赖的信号——两个或多个类互相引用，Spring 无法决定先创建谁。这导致：
- 启动顺序不确定（谁先初始化靠运气）
- 测试时无法 mock 依赖（必须启动完整 Spring 上下文）
- `@Lazy` 代理的 NPE 风险（如果在代理完成前被调用）

**改动影响**: 大。但几乎全部是机械性重构——把 `@Autowired private X x` 改成构造函数参数。约 44 个文件，每个 5-10 分钟，合计 1 人天。

**修复优先级**: 建议先修。这是后续所有架构改进的基础——God Service 拆分必须建立在清晰的依赖图之上。

### S14. 33 Controller 直接调 Mapper 🔴

**数据**: 33 个 Controller 绕过 Service 层直接操作 Mapper。最大违规者：
- `StudentMobileCenterController.java` (861 行)：直接使用 6 个 Mapper
- `MonitorController.java` (902 行)：直接使用 `TwinAutomationLogMapper`

**影响**: 业务逻辑和 SQL 查询混在 Controller 中，无法单独测试、无法复用、无法做事务管理。

**改动影响**: 大。每对 Mapper 调用需要提取到对应 Service 中。但可以渐进式做——每次改一个 Controller-Mapper 对。不需要一次性完成。

### S15. 36 God Service 超过 500 行 🔴

| Service | 行数 | 可能拆分方向 |
|---------|:---:|------|
| `MaterialService` | 1,930 | CRUD / 审批工作流 / 通知 / ARO 集成 |
| `AssetService` | 1,885 | CRUD / 折旧计算 / 盘点 / 报表 |
| `FacilityMaintenanceService` | 1,600 | 报修 / 派单 / 完工 / 评价 |
| `SuppliesService` | 1,595 | 申领 / 审批 / 库存 / 采购 |
| `AccessSwingCleanWorkspaceService` | 1,590 | — |

**改动影响**: 很大。拆分为 3-5 个聚焦 Service 需要理解现有业务逻辑。不能机械拆分——必须理解每个方法属于哪个子域。建议在项目空闲期分批次做，每次拆 1 个 God Service。

### S16. twin 模块 15 路辐射依赖

**数据**: `twin` 模块被其他 15 个模块引用，形成中心辐射型依赖图。`me` 模块（个人中心）也引用了 12 个其他模块。

### 🔴 NS13. BCrypt 密码哈希在管理员 API 响应中泄露

| 属性 | 值 |
|------|-----|
| **位置** | `AdminMapper.xml:15,57` → `AdminController.java:38-58` |
| **对应标准** | OWASP A02 加密失败 / CWE-522 凭据不足的防护 |

**服务端**（`AdminMapper.xml`）：

### 🔴 NS14. JWT 令牌无吊销机制 — 泄露即永久有效

| 属性 | 值 |
|------|-----|
| **位置** | `JwtTokenService.java` 全类 |
| **对应标准** | NIST SP 800-63B §4.1.4 令牌管理 / OWASP ASVS V2.2.3 |
| **置信度** | **9/10** |

**事实**：
- JWT 签发后 30 天有效（`JwtTokenService.java:57`），可刷新至 60 天（`JwtTokenService.java:176-177`）
- **无任何黑名单、吊销列表或令牌失效机制**
- 密码修改不清除已有 JWT（用户改密后旧 Token 仍有效）
- 角色变更不清除已有 JWT（权限降级后旧 Token 仍保留原角色）
- 用户禁用不清除已有 JWT（仅检查 `status != 0`，可在下一次请求时拦截，但已颁发的模拟 Token 不受影响）

**攻击场景**：
1. Token 通过 XSS、日志泄露、中间人攻击被窃取
2. 用户发现异常后修改密码 → 攻击者的旧 Token **仍然有效长达 30 天**
3. 用户被管理员降权 → 旧 Token 仍然保留原高权限角色（角色编码在 JWT claims 中）

**修复**：
1. **短期**：在 `sys_user` 表添加 `token_version` 列，JWT claims 中包含此版本号，验证时比对。密码修改/角色变更/管理员强制下线时递增版本号 → 所有旧 Token 立即失效
2. **中期**：实现 Redis 黑名单，关键操作（密码修改、角色变更）时将被吊销 Token 的 jti 加入黑名单（TTL = Token 剩余有效期）
3. **长期**：迁移至 OAuth 2.0 / OpenID Connect 会话管理体系

### 🟠 NS18. CSRF 保护完全缺失

| 属性 | 值 |
|------|-----|
| **位置** | 全局（无 Spring Security，无自定义 CSRF Filter） |
| **对应标准** | OWASP A05 安全配置错误 / ASVS V4.2 |
| **置信度** | **8/10** |

**事实**：
- `pom.xml` 不包含 `spring-boot-starter-security` → 无 Spring Security CSRF 保护
- 全量代码搜索 "csrf" → **零结果**
- 所有 POST/PUT/DELETE/PATCH 端点依赖 Bearer Token 认证，**无 CSRF Token**
- CORS `allowCredentials(false)` 限制了基于 Cookie 的 CSRF，但不阻止基于 Token 的跨站请求

**攻击场景**（结合已发现漏洞）：
1. 攻击者通过 NS12 存储型 XSS 获取学生 JWT
2. 或通过 NS1 mock token 构造任意 Token

4. 但在同源页面中（XSS），攻击者可自由发起任何 API 请求

**结论**：在 Bearer Token 架构下，CSRF 风险低于 Cookie-Session 架构，但结合 XSS 漏洞后风险显著上升。修复 XSS 比添加 CSRF Token 优先级更高。

**修复**：
1. **优先**：修复所有 XSS 向量（NS12）
2. **补充**：对关键状态变更端点（密码修改、角色变更、删除操作）添加自定义 `X-Requested-With: XMLHttpRequest` 或 `Origin` 头校验

#### 🔴🔴 NS27. /api/admin-nav 完全无认证 — 拦截器路径不匹配极危

| 属性 | 值 |
|------|-----|
| **位置** | `AdminNavConfigController.java:11` + `WebMvcConfig.java:36` |
| **对应标准** | OWASP API5:2023 功能级授权失效 |
| **置信度** | **10/10** |

**根因**：`AdminNavConfigController` 映射到 `@RequestMapping("/api/admin-nav")`，而 `AdminAuthInterceptor` 注册路径为 `addPathPatterns("/api/admin/**")`。Ant 路径模式 `/api/admin/**` **不匹配** `/api/admin-nav`（因为 `**` 只展开路径段，不匹配 `-` 连接的前缀变体）。

**受影响端点**（全部 9 个，零认证）：
```
GET    /api/admin-nav/config          — 返回完整导航配置树
POST   /api/admin-nav/groups          — 创建导航分组
PUT    /api/admin-nav/groups/{id}/move — 移动分组
PUT    /api/admin-nav/groups/{id}     — 更新分组
DELETE /api/admin-nav/groups/{id}     — 删除分组
PUT    /api/admin-nav/items/{id}/move — 移动导航项
PUT    /api/admin-nav/items/reorder   — 重排导航项
POST   /api/admin-nav/ensure-items    — 创建导航项
POST   /api/admin-nav/reset           — 重置全部配置为默认值
```

**攻击演示**：
```bash
# 无需任何认证，直接读取全部导航配置（含所有管理员菜单结构）
curl "https://target/api/admin-nav/config"

# 无需认证，重置导航配置 → 发起 DoS 或注入恶意导航 URL
curl -X POST "https://target/api/admin-nav/reset"
```

**修复**：将 `WebMvcConfig.java:36` 改为 `addPathPatterns("/api/admin/**", "/api/admin-nav/**")`。

#### 🟠 NS31. KnowledgePageRenderer 富文本路径零消毒 XSS

| 属性 | 值 |
|------|-----|
| **位置** | `KnowledgePageRenderer.tsx:7-13` |

```typescript
const html = useMemo(() => {
    const md = contentMd?.trim();
    return md ? renderMarkdownToSafeHtml(md, "light") : (contentHtml || "");
    // ⚠️ 当 contentMd 为空时，contentHtml 直接使用，未经过 DOMPurify！
}, [contentHtml, contentMd]);
return <article dangerouslySetInnerHTML={{ __html: html }} />;
```

Markdown 路径经过 `renderMarkdownToSafeHtml` → DOMPurify ✅。但富文本路径 (`contentHtml`) **完全绕过消毒**。若攻击者能注入恶意 HTML 到知识库页面内容，所有查看者浏览器中将执行脚本。

**修复**：`contentHtml || ""` → `sanitizeRichTextHtml(contentHtml || "")`。

#### 🟠 NS32. Supply/Material 库存竞态 — 并发超卖

| 属性 | 值 |
|------|-----|
| **位置** | `SuppliesService.java:517-540`，`MaterialService.java:431-436` |

申领创建时先 `SELECT` 读取库存 → 校验 → 扣减。两个并发请求读到相同库存量后均可通过校验，导致超卖。`decreaseStockIfEnough` 的 SQL 级 `WHERE stock_qty >= ?` 防护了扣减步骤但**不防护校验步骤**。

**修复**：`SELECT ... FOR UPDATE` 锁定库存行后再校验扣减。

> **第三轮审计结论**:
>
> **第一轮**（原审计 S1-S22）覆盖了配置和架构层面。**第二轮**（补充审计 NS1-NS11）发现了代码逻辑层面的 11 个漏洞，其中 4 个极危零知识接管。**第三轮**（OWASP 标准对齐 NS12-NS26 + 并行代理新发现 NS27-NS35）对照 OWASP Top 10、OWASP API Top 10、OWASP ASVS 4.0、NIST SP 800-63B、CWE Top 25 进行系统性缺口分析 + 4 路专项代理攻击面探索（IDOR/Mass Assignment/XSS/数据暴露/认证缺口），新发现 24 项缺陷。
>
> **四轮合计**: **57 项缺陷**（原 22 + 第二轮 11 + 第三轮 15 + 第四轮 9）。其中：
> - 🔴🔴 极危（零知识远程接管）: 6 项（NS1, NS2, NS5, NS6, NS27, NS28）
> - 🔴 阻断（生产准入阻塞）: 12 项（S1-S6, NS3, NS4, NS7, NS12, NS13, NS14, NS29）
> - 🟠 高（生产前修复）: 17 项
> - 🟡 中（首次迭代后修复）: 19 项
> - 🟢 低: 2 项 (S21, S22)
>
> **P0 修复（10 项极危+数据泄露）预计 6 小时。P0+P1 全部准入条件（28 项）预计 4-6 个工作日。**
>
> **关键洞察**：
> 1. 最严重的遗漏是 **NS27** (/api/admin-nav 无认证) 和 **NS28** (扫码终端 8 端点无认证) — 这些是部署边界错误：原本应通过内网隔离或硬件 Token 保护的端点被暴露在公网路径下且零认证
> 2. 攻击面最大的漏洞组合是 NS1 (mock token) + NS12 (存储型 XSS) + NS28 (扫码终端无认证 PII) — 攻击者可读取全校人员数据、修改门禁卡绑定、向所有学生推送 XSS
> 3. NS28 涉及**物理安全**：大华门禁卡绑定和强制签离端点无认证意味着攻击者可操控物理门禁系统
> 4. 最严重的合规缺口是 NS17 (无审计追踪) + NS14 (无令牌吊销) + NS35 (GDPR/PIPL) — 使安全事故既无法预防也无法追溯，且违反数据保护法规
> 5. SELECT * 反模式 (NS15)、Map @RequestBody (NS16)、零校验注解 (NS33) 是设计层面的"定时炸弹"——当前未被利用，但未来代码变更极可能引入可被利用的路径
> 6. 本项目安全防护的最大结构性问题不是单个漏洞，而是**缺乏纵深防御** — 认证、授权、审计、日志、传输加密五层中四层严重薄弱
