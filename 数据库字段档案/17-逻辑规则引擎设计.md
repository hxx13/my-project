# 17-逻辑规则引擎设计

> 状态：**设计态（深设计）**。本文件解决 14 复盘的 #5（关键逻辑核查规则）与 #6（访视窗口规则）。逻辑规则是「可配置的数据」，不是硬编码 if-else。

## 一、背景与需求（来源）

- **关键逻辑核查**（最低标准 §步骤3）：血肌酐超 NHP 参考范围弹窗、免疫抑制剂血药浓度低于目标值标记、样本采集时间与访视时间差 >3 天报警。
- **访视窗口规则**（建设方案 §3.4）：TP 时点允许偏差由动物中心提出，随 V1.0 冻结确认。

## 二、核心区分：字段级校验 vs 访视级窗口

| 层 | 规则 | 落点 | 说明 |
|---|---|---|---|
| 字段级 | 范围 / 阈值 / 时间差 / 跨字段 / 正则 | `crf_validation_rule` | 针对单个字段值的校验 |
| 访视级 | TP 时点窗口偏差 | `crf_visit.window` | 针对「访视发生时间」的偏差，动物中心可配 |

> 关键：访视窗口规则不是字段校验，是「访视定义」的属性，落在 `crf_visit`（05 已设计），不混进字段校验规则。

## 三、规则类型全集（字段级，6 类）

| rule_type | 含义 | expression JSON 参数 | 对应 Word 例子 |
|---|---|---|---|
| RANGE | 数值范围校验 | `{ref_range_id}`（引用 crf_reference_range 分层参考范围表） | 血肌酐按种属/性别/年龄分层参考范围 |
| THRESHOLD | 阈值标记 | `{op: "lt"/"gt", value, reference}` | 血药浓度低于目标值 |
| TIME_GAP | 时间差校验 | `{fieldA, maxDays, op}`（比较对象是 visit_instance.actual_date，**跨实体**，非字段） | 样本采集与访视差 >3 天 |
| CROSS_FIELD | 跨字段一致性 | `{fieldA, op, fieldB}` | 数量/明细相互印证 |
| REGEX | 格式校验 | `{pattern, message}` | 编号格式 |
| ENUM | 枚举约束（已由码表/字段约束覆盖） | `{codelist}` | 取值必须在码表内 |

## 四、规则数据模型（crf_validation_rule 具体化，承接 05）

05 已设计的 `crf_validation_rule`（field_id + rule_type + expression JSON），本文件定死 expression 格式：

| 列 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | |
| field_id | BIGINT FK → crf_field | 针对哪个字段 |
| rule_type | VARCHAR(20) | RANGE / THRESHOLD / TIME_GAP / CROSS_FIELD / REGEX / CONDITIONAL_REQUIRED / SKIP |
| severity | VARCHAR(10) | WARN（提醒可继续）/ ERROR（阻止必须改）/ FLAG（仅标记，如血药浓度低） |
| expression | JSON | 按 rule_type 取参数（见上表） |
| message | VARCHAR(255) | 触发时的提示文案 |
| active | TINYINT | 软删 |
| created_at | DATETIME | |

### expression 示例（落库 JSON）

```json
{ "rule_type": "RANGE", "expression": { "min": 0, "max": 200, "unit": "μmol/L" }, "severity": "WARN" }
{ "rule_type": "THRESHOLD", "expression": { "op": "lt", "value": 8.0, "reference": "他克莫司谷浓度目标值" }, "severity": "WARN" }
{ "rule_type": "TIME_GAP", "expression": { "fieldA": "collect_datetime", "fieldB": "visit_date", "maxDays": 3 }, "severity": "ERROR" }
```

### 4.1 分层参考范围表（RANGE 引用，新增）

血肌酐/血常规等参考范围按「种属/性别/年龄带」分层，单条 `{min,max}` 表达不了，需独立表：

| crf_reference_range 列 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | |
| field_id | BIGINT FK → crf_field | 针对哪个检验字段 |
| species / sex / age_min / age_max | VARCHAR/INT | 分层维度 |
| min / max | DECIMAL | 参考范围 |
| source / version | VARCHAR | 参考范围来源（动物中心/实验室）+ 版本 |
| active | TINYINT | |

RANGE 规则的 expression 改为 `{ref_range_id}` 引用此表，不再内嵌数值。

## 五、访视窗口规则（crf_visit 增加列）

| crf_visit 新增列 | 类型 | 说明 |
|---|---|---|
| early_days | INT NULL | 允许提前天数（如 TP05 提前 2 天），由动物中心配置 |
| late_days | INT NULL | 允许延后天数（TP01 是 -28~-7d 区间、TP12 是 +30d，非对称，需两列） |

- 时点窗口校验：实际访视日期超出 `TP 锚点 -early_days ~ +late_days` 时标记（WARN）；TP10 事件触发类时点无锚点，跳过窗口校验。
- 这是「访视级」规则，执行时机在访视实例（crf_visit_instance）保存时，不在字段录入时。

## 六、规则执行引擎

### 触发时机（4 处，复用同一引擎）

1. 字段录入保存时（实时校验）
2. 数据导入校验（16 的导入流程第 3 步）
3. 表单提交/复核时（批量核查）
4. 双录入比对后

### 执行流程

```
录入值 → 取该字段的 active 规则列表 → 逐条 evaluate
       → 通过 / WARN（提示可继续）/ ERROR（阻止，需修正或写原因）
       → 结果写审计（crf_data_audit_log，change_reason=校验触发）
```

### 引擎实现（纯函数，可单测）

- `evaluateRule(rule, value, ctx): { pass: boolean, message?: string }`
- `evaluateFieldRules(fieldId, value, ctx): ValidationResult[]`
- 规则引擎是**纯函数**，不依赖 UI/网络，放在 `store/` 或独立 `engine/` 层（承接 13 分层）。

## 七、与显隐规则（showWhen）的边界

- `showWhen`（12 已设计）= **显隐**：控制字段「显示/隐藏」，不校验值。
- `crf_validation_rule` = **校验**：校验值「对不对」，不控制显示。
- 两者独立，但都引用其它字段取值（连锁关系），共用 `buildFieldCatalog`（15 的工具函数）。

## 九、对底层代码架构的影响（承接 13）

- 规则引擎是**独立一层**（`features/nhp/engine/`），纯函数，被「录入」「导入」「复核」三处复用。
- 规则是**数据**（crf_validation_rule 表），引擎是**纯函数**（evaluate），配置和逻辑分离。
- 与 16 数据导入层衔接：导入校验直接调用本引擎，不写第二套校验。
