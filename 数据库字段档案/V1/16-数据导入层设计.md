# 16-数据导入层设计

> 状态：**设计态（深设计）**。本文件解决 14 复盘里标「最关键」的两个遗漏：#1 双轨采集+回溯录入、#2 外部数据对接。这是需要全局理解才能做的设计——它要和 EAV 数据层（06）、业务流转（09）、审计（06 第四节）三者咬合。

## 一、背景与需求（来源）

- **双轨采集**（建设方案 §5.3）：T0 当天纸版 CRF + Excel 兜底采集 → T0+2 周**回溯录入** EDC → 作为 UAT 真实测试集。
- **外部数据对接**（最低标准 §步骤4 源文件映射）：供体健康记录、基因鉴定报告、**仪器导出 CSV 批量导入**、病理报告、样本库台账。
- **ALCOA+ Contemporaneous**（建设方案 §6.1）：同步记录，要能追溯「数据是什么时候采集的」。

## 二、核心洞察：采集时间 ≠ 录入时间

双轨采集的本质：**数据是「事后录入」的**。纸版/Excel 在 T0 采集，T0+2 周才录进 EDC。所以每条值要分离两个时间：

| 时间 | 含义 | 落点 |
|---|---|---|
| `collected_at` 采集时间 | 数据**实际发生/采集**的时刻（T0 当天） | 新增列，追溯 ALCOA+ |
| `created_at` 录入时间 | 数据**录入 EDC** 的时刻（T0+2 周） | 已有列 |

**这是 06 的 `crf_record_value` 缺失的关键列**——没有它，回溯录入的数据会「丢失采集时间」，违背 ALCOA+ 的 Contemporaneous。

## 三、三条录入路径（source_type）

| 路径 | source_type | 场景 | collected_at 来源 |
|---|---|---|---|
| 手工表单录入 | `MANUAL` | 实时采集（术后随访、用药） | ≈ created_at（默认） |
| 批量导入 | `IMPORT` | 仪器 CSV / 检测结果回传 | 源文件时间列（映射） |
| 纸版回溯录入 | `PAPER` | T0 纸版/Excel 兜底 → 事后录入 | 手工填「采集时间」（录入 UI 强制要求） |

## 四、表结构设计

### 4.1 修改 crf_record_value（06 已设计，增 3 列）

| 新增列 | 类型 | 说明 |
|---|---|---|
| `collected_at` | DATETIME NULL | 采集时间；MANUAL 默认=created_at，IMPORT/PAPER 必填 |
| `source_type` | VARCHAR(20) NOT NULL DEFAULT 'MANUAL' | MANUAL / IMPORT / PAPER |
| `source_ref` | VARCHAR(64) NULL | 来源引用：导入批次 ID 或源文件 ID |

### 4.2 新增 crf_import_batch（导入批次）

| 列 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | |
| form_id | BIGINT FK → crf_form | 导入到哪个表单（数据域） |
| file_format | VARCHAR(20) | CSV / EXCEL / PAPER（batch 层用 file_format，避免与 record_value.source_type 同名异义） |
| file_id | BIGINT NULL FK → upload_file_record | 导入源文件（复用现有附件表） |
| operator_id | VARCHAR(64) | 操作人 personnel.id |
| mapping_json | JSON | 分层字段映射：sheet→form、列组→字段/重复组、键列定位（见下方示例） |
| status | VARCHAR(20) | PENDING / VALIDATED / IMPORTED / FAILED |
| total_rows / success_rows / failed_rows | INT | 导入统计 |
| error_json | JSON NULL | 失败行 + 原因 |
| created_at | DATETIME | |

> 字段映射 `mapping_json` 是**分层结构**（非平面字典），承载多 sheet、重复组、键列定位。示意：
> ```json
> {
>   "sheets": [
>     { "sheet": "血常规", "form": "D4",
>       "keys": { "__subject_code__": "猴号列", "__visit_tp__": "TP列", "__tx_id__": "TX列" },
>       "columns": { "WBC": "D4.02.001", "RBC": "D4.02.002" } },
>     { "sheet": "用药", "form": "D6",
>       "repeat": { "group": "每次给药", "columns": { "药物": "D6.02.003", "剂量": "D6.02.004" } } }
>   ],
>   "collectedAt": { "column": "采集时间", "fallback": "visit_date" }
> }
> ```
> - 保留键列 `__subject_code__`/`__tx_id__`/`__visit_tp__`：用于定位/创建 crf_record + crf_visit_instance，缺省策略「找不到即建，冲突报错」。
> - `repeat`：重复组展开（D6 每次给药、D10 每3h），一行展开成多条 record_value。
> - `collectedAt.fallback`：采集时间列缺失时的回退（访视日期 → 文件创建时间）。

## 五、导入流程（5 步）

```
1 上传源文件（CSV/Excel → upload_file_record）
2 字段映射（源列 → 字段字典字段，含 __collected_at__ 保留字）
3 校验（类型/范围/必填，复用逻辑规则引擎见 17）
4 落库（写入 crf_record_value，source_type=IMPORT，source_ref=batch_id）
5 审计（写 crf_data_audit_log，change_reason=导入；来源标记 source_ref/collected_at 落在 crf_record_value，不落审计表）
```

- 校验失败的行**不落库**，进 `error_json` 待人工修正后重导。
- 纸版回溯录入（PAPER）不走文件上传，走「手工录入 + 强制填采集时间」的专用入口。

## 六、审计与 UAT 对接

1. **导入审计**：每批导入写 `crf_data_audit_log`（change_reason=`导入`，operator=操作人），来源标记落在 `crf_record_value.source_ref = batch_id`（审计表不含 source 列，见 06），保证导入数据与手工录入同等留痕。
2. **回溯录入 UAT**：首例 T0 数据在 T0+2 周回溯录入，作为 UAT 真实测试集——`source_type=PAPER` 的数据天然标记了「哪些是回溯录入」，UAT 可据此统计「双轨一致性」（纸版值 vs EDC 录入值的一致性核查）。
3. **一致性核查**：双轨期纸版/Excel 兜底数据须与 EDC 回溯录入做一致性比对，比对结果作为 UAT 通过依据。

## 八、对底层代码架构的影响（承接 13）

- 数据导入是**独立的一层**（`features/nhp/import/`），与「手工录入层」「表单模板层」并列，不是塞在表单控件里。
- 三层：`import/`（导入 UI + 字段映射）→ `store/`（导入状态）→ `api/`（上传 + 导入端点）。
- 导入校验复用「逻辑规则引擎」（下一份设计 17），不做第二套校验逻辑。
