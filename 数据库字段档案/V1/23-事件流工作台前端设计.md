## 1. 为什么放弃「表单为中心」（核心诊断，4 条）

1. **单位错位**：EDC 表单的单位是「域」（D1 供体 / D5 随访），实验记录的单位是「事件」（采血 / 给药 / 记体征）。把内部 schema 的「域」直接暴露成「录入页面」，是让用户替数据模型打工。
2. **时间被降维**：临床 CRF 把时间当「访视编号」，一次填一页；动物实验的时间序列是连续高频的（术中每 5–15min、术后每日、血药谷/峰）。把 100 次随访塞进「重复填同一表单」= 用表格软件存一维数组。
3. **录入场景错配**：双录入（一录/二录）是「抄录员对照纸版转录」的法规动作（ICH-GCP），这里是一线实验者边做边记，要的是快/准/顺手。
4. **role 加在表单上是补丁**：即便给 29 字段扁平表单加 PK/FK/DERIVED，单位仍是「表单」，没变。

---

## 2. 新范式三句话

- **以研究对象的时间线为画布**（day 0 = tx_date 锚点）。
- **动作为「记录事件」**（采血 / 给药 / 记体征 / 送检 / 报 AE / 随访…）。
- **录入按数据性质分三种形态**，不由「域」决定。

## 3. 信息架构（页面地图）

```
对象列表（供体 / 受体，带状态卡）
   └─ 对象时间线工作台（day 0 锚点）
        ├─ 时间线（TP01~TP12，导航 + 频次 + 当前）
        ├─ 今日待办（调度引擎推送）
        ├─ 「＋记录事件」→ 三种形态
        │     ├─ 事件面板（一次性事件：配型/手术/活检/终点/送检委托）
        │     ├─ 序列网格（测量序列：体征/检验/浓度/免疫指标）
        │     └─ 台账列表（重复子实体：样本/给药/AE/CoC 交接）
        └─ 对象维度子页（可下钻：某样本的送检→结果链路）
```

**入口粒度决策**：首页是「对象列表」，不是「模板列表」。模板/字典/码表退到**配置侧**（管理端），采集侧只见「对象 + 事件」。

## 4. 三种录入形态规格

### 4.1 序列网格（测量序列）
- **适用**：生命体征、检验结果、血药浓度、免疫指标、随访指标（计划里「测量序列」模式出现 6 次的那些）。
- **结构**：行 = 时点/时间，列 = 指标，单元格 = 值。异常值按参考范围自动高亮（▲ 高 / ▼ 低）。
- **交互**：内联编辑 + 「＋加一行」；支持**批量连录**（术中连续记多行体征）。
- **为什么是网格不是表单**：时间序列的自然形态是表/曲线，不是重复字段块。
- **趋势**：网格旁可选 sparkline / 曲线视图（后续），当前先做表。

### 4.2 台账列表（重复子实体）
- **适用**：样本、给药、不良事件、CoC 交接事件（计划里「父+子实体」的「子」）。
- **结构**：列表，每条一个**自动编号**（PK 取号）+ 摘要 + 时间 + 状态。
- **交互**：「＋新增」弹事件面板；每条可展开看详情；可筛选/排序。
- **关键**：台账条目之间有关联链（样本 → 送检 → 结果 = CoC 链路），下钻展示。

### 4.3 事件面板（一次性结构化事件）
- **适用**：配型、手术、麻醉、活检/病理、终点、送检委托——「一台手术一条 / 一次取材一条」类。
- **结构**：紧凑面板（弹层或抽屉），字段集小、针对性强，绑定「对象 + 时点」。
- **与「表单」的本质区别**：表单以「域」为单位让用户填 50 字段；事件面板以「这次发生了什么」为单位，只出现这件事该填的字段，且 role 自动化掉不该手填的部分。

## 5. 事件类型 × role 自动化映射

| 事件 | 主键 PK（取号器） | 外键 FK（选择器） | DERIVED（计算） | 形态 |
|---|---|---|---|---|
| 采血样本 | `SMP-{TX}-{TP}-{类型}-{分管2}` 自动连号 | 关联 TX / 时点 | — | 台账 + 面板 |
| 给药 | `MED-{REG}-{序号4}` 自动连号 | 关联方案 REG | 谷/峰提醒、间隔推算 | 台账 + 面板 |
| 生命体征 | 无独立 PK（序列） | 关联时点 | 异常值判定、趋势 | 序列网格 |
| 检验结果 | `RS-{TEST_ID}-{项目码}` | 关联送检单 + 项目码 | QC 状态机、参考范围判定 | 序列网格 / 台账 |
| 送检委托 | `TST-{实验室}{年月}-{序号4}` | 多选样本 | — | 事件面板 |
| 不良事件 | `AE-{TX}-{日期}-{序号2}` | 关联 TX / 活检样本 | 分级/结局状态机 | 台账 + 面板 |
| 随访访视 | `FU-{TX}-{TP}-{seq:2}` | 关联 TX | 时点窗口偏差 | 事件面板 |
| 配型 | `XM-{DONOR}-{RECIP}-{seq:2}` | 供受对 | 配对评分（算法 V1） | 事件面板 |
| 手术 | `TX-{中心}{年}-{序号3}` | 供体/受体/采用的 XM | day0 锚点 | 事件面板 |
| 活检/病理 | `PATH-{TX}-{时点}-{seq:2}` | 关联样本 / AE | 排斥分级（D8 权威） | 事件面板 |

**role 自动化原则**：PK 打开面板即生成（灰锁只读）；FK 从台账/实体列表勾选（蓝）；DERIVED 只读计算并显式标注算法来源（青）；VALUE 才允许手填（码表/直填）。

## 6. 调度 / 待办引擎（新维度）

- **输入**：`crf_visit` 的 TP 定义 + 原子挂的 schedule（时点范围 + repeat 频率）+ tx_date（day 0 原点）。
- **输出**：对象时间线上的「待办」——**今日该做什么**，而非等用户去找表单。
- **三类待办**：
  - 计划访视待办（TP04 每日 panel、TP05 每周 2 次…）——schedule 展开生成。
  - 衍生待办（血药谷浓度、给药间隔）——由 role/DERIVED 规则推。
  - 事件触发（TP10）——AE 等触发加采，不受时点表限制。
- **逾期判定**：计划时点 vs 当前时间 → 逾期（红）/ 即将到期（黄）/ 正常（灰）。
- 这是「调度层」第一次真正「推」给用户，是事件流范式区别于表单范式的标志。

## 7. 配置侧与采集侧边界（关键）

表单范式下，字典/模板/码表是「录入前必须配好、录入时直接摊开」的东西。事件流范式下，两者职责分离：

| 侧 | 谁用 | 页面 | 职责 |
|---|---|---|---|
| **配置侧**（管理端） | 平台 DM / PI | 字段字典、模板、码表、方案库、panel 版本 | 定义「每个事件类型有哪些字段、role 是什么、码表是什么」 |
| **采集侧**（门户/一线） | 实验者/兽医/护士 | 对象列表 → 时间线工作台 | 只做「记录发生了什么」，看不见「域」 |

**含义**：现有的 `NhpTemplateEditor` / `NhpFieldPage` / `NhpCodelistPage` 不删，但它们**只服务于配置侧**，不再作为采集侧的入口。采集侧的事件面板/网格/台账，由配置侧的「事件类型定义」驱动生成（字段集 + role 行为来自配置，不是硬编码）。

## 8. 关键交互细节（待 v3 逐条视觉化）

1. **PK 取号时机**：打开「＋采血」即预生成样本号（可改分管导致重排），保存时落库——避免「填一半的号」与「并发重号」。
2. **FK 选择器数据源**：给药→方案库（版本化）；送检→样本台账（勾选，多对多）；活检→样本 + AE。
3. **CoC 链路下钻**：样本台账里点开一条样本 → 看到「委托单 TST → 结果 RS → QC 状态」，链路断裂（无结果回传）标红。
4. **异常值**：网格单元格按 `crf_reference_range`（种属/性别/年龄分层）自动 ▲▼；超限提示。
5. **剂量 value+unit 锁定**：给药/方案剂量拆 `dose_value` + `dose_unit`，单位从码表锁，不自由文本。

## 10. 与后端数据模型的对应（供后端实现对齐）

| 前端概念 | 后端 |
|---|---|
| 对象时间线 | `crf_visit`（TP 定义）+ `crf_visit_instance`（实际访视）+ tx_date 原点 |
| 事件面板 | 实体表（`crf_sample`/`crf_medication`/`crf_adverse_event`/`crf_transplant`/`crf_pathology`…） |
| 序列网格 | EAV（`crf_record_value`）+ 原子标「序列类型+频率」 |
| 台账 | 实体子表（父+子） |
| role 自动化 | `crf_form_field.role`（PK/FK/VALUE/DERIVED）+ 取号器 + 计算引擎 |
| 待办/调度 | 访视展开引擎（计划 ④ 调度层，尚未接进链路） |

> 关键：**后端五层数据模型（字典→原子→组合→调度→数据）基本不变，改的是「交互层如何消费它」**——把「域」从采集侧入口降级为配置侧组织方式，把「事件 + 时间线」提为采集侧第一公民。

## 11. 配置侧「事件类型定义」层（v4 新增，地基）

- **核心关系**：采集侧的事件面板 / 网格 / 台账 = 配置侧「事件类型定义」的**运行态投影**。前端不硬编码事件面板——字段集、role 行为、取号规则、录入形态全部由配置驱动。
- **事件类型 ≈ 计划里的「原子」**：原子按「子模块 × 重复频率」切，事件类型按「发生了什么」切，两者**一一对应**。差别只是视角——原子是数据模型视角，事件类型是交互视角。
- 每个事件类型定义包含：实体表（`crf_sample`/`crf_medication`/…）、录入形态（面板/网格/台账）、主键编码规则（SMP/MED/AE/…）、时点范围 + 重复频率、字段集（每字段标 role：PK/FK/VALUE/DERIVED）。
- **归属多态**（样本的 tx_id OR donor/recipient_id）在事件类型层显式声明，前端据此决定 FK 选择器的数据源。
- 配置侧入口：`/#/content-manager/nhp-events`（新页面，替代「域」作为采集侧的结构来源）。

## 12. 随访访视面板（v4 新增）

- **访视是「容器」，不是「域表单」**：一次访视 = 一组该时点该做的**事件清单**（采血 panel ×N、体征 ×N、给药、AE 筛查…）。
- 清单项各自是独立事件，点击进入各自的事件面板/台账，**互不混在一张 50 字段表单里**——这是它区别于「D5 域表单」的根本。
- 清单由 schedule 展开 + 事件类型定义**自动生成**（TP04 每日 → 采血/体征/给药；TP05 每周2次 → 另加免疫指标）。
- 完成度（如 4/6）是**访视进度**，不是字段完成度。

## 13. 序列网格增强（v4 新增）

- **批量连录**：术中（每 5–15min）/ 术后高频（每 4h）的体征，本质是「按固定节奏往同一张表追加行」。批量连录一次填多行，时间戳按间隔**自动递增**——不重复「＋加一行 → 填时间 → 填值」四遍。
- **趋势曲线**：网格旁切换「表格 / 趋势」，共用同一份 `crf_reference_range` 做异常高亮。
- 两者都服务「高频序列要快、要看出趋势」，不增加表单感。

## 14. 流程优化（v5，评审前自检）

### 14.1 概念闭环：事件类型 = 原子（交互投影，非新层）

修正 §9 的模糊表述——**事件类型不是介于「域」和「原子」之间的新抽象层**，它就是原子在采集侧的投影：

| 层 | 定义 | 归属 |
|---|---|---|
| 域（D1–D10） | 字典组织方式（字段归域/子模块） | 配置侧 |
| 原子 | 数据单元 = 子模块 × 重复频率（计划 D2 决策） | 数据层 |
| **事件类型** | 原子的交互命名 + 交互元数据（形态/取号规则/角色权限） | 采集侧 |

三者一一对应：`D4.01 样本台账 → 采血样本 → 台账+面板`；`D7.02 监护序列 → 生命体征 → 序列网格`。**无需第三抽象层**，配置侧「事件类型定义」页 = 原子配置页的交互增强版。

### 14.2 完整生命周期时间线（术前锚 ≠ day0 锚）

修正 v3/v4 只画术后 day0 的缺口——**时间线锚点随生命周期演进，不是一上来就有 day0**：

- **术前**（供体准备 / 受体预筛 / 配型）：无 day0，锚定「入组日 / 计划手术日」，相对 -28~-7d 筛查、-1~0d 基线。
- **手术**：tx_date 确定 → day0 锚点建立。
- **术后**：day0 锚定，TP04~TP12 随访时间线展开。

对象状态机：`预筛中 → 配型中 → 移植后 → 终点`，时间线视图随状态切换。供体侧同构（基因编辑 → 病原监测季度 → 器官出厂判定）。

### 14.3 事件驱动链（「流」真正落地）

事件不只「记录」，还「驱动下游」——这是「事件流」的「流」字落地处：

- 采血 → 自动生成送检待办 → 结果回传 → QC 复核
- 手术完成 → 展开术后随访时间线 + 生成 TP04 待办
- AE 报告 → 触发 TP10 事件加采 + 可选活检
- 给药 → 生成谷浓度待办
- 配型通过 → 进入手术排期

**待办引擎 = 事件驱动链的执行器**：每条事件入库后，按事件类型定义的「下游规则」生成/推进待办，而非只落一条数据。

> 后端承载已补（评审闭环）：见 `22-NHP后端改造实施计划.md` §6.3「事件规则引擎」——`crf_event_rule`（源事件 + 触发时机 → 动作）+ `crf_todo`（待办 materialized，双源 SCHEDULE/EVENT_RULE），动作四种 `EXPAND_SCHEDULE` / `GENERATE_TODO` / `CREATE_EVENT` / `ADVANCE_STATE`。采集形态推导（capture_form=SERIES/LEDGER/PANEL）见 22 §6.1。

### 14.4 轻量复核（砍双录入后的质量保证）

砍掉一录/二录后，质量由「关键事件必复核 + PI 抽查 + DM 核查（CoC 断裂/异常值）」承接，落在采集侧为一条「待复核」队列——不回到表单，不引入双录入。
