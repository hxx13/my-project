# 27-NHP 信息架构与入口设计

> 状态：**深设计进行中**。回答四个问题：页面显示在哪、深度怎么排、入口在哪、要不要总入口。
> 前置：`23 采集侧` / `24 配置侧` / `25 治理辅助` 定义了「有什么页面」，本文定义「怎么摆」。

---

## 0. 核心结论（一句话）

**双端 + 一个总入口**：门户侧（采集，3 层）管「记数据」；管理端（配置+治理，2 层为主）管「配字典/审质量」；管理端顶一个「**NHP 研究总览**」做总入口（状态看板，非流程引导），桥接两端。

---

## 1. 双端结构（谁用哪侧）

| 端 | 谁用 | 管什么 | 深度 |
|---|---|---|---|
| **门户侧**（`/nhp`） | 实验者/兽医/护士/一线 PI | 记录发生了什么（采集） | 3 层 |
| **管理端**（`/content-manager/nhp-*`） | 平台 DM / PI / 研究员 | 配字典 + 审质量（配置+治理） | 2 层为主 |

## 2. 门户侧 IA（采集，3 层）

```
门户首页
  └─ 「NHP 研究计划」入口卡片（现有：实验动物 → 手术 → NHP研究计划）
       └─ ① 对象列表（/nhp）           ← 采集侧首页
            └─ ② 时间线工作台（/nhp/:subjectId）
                 ├─ 序列网格 / 台账 / 事件面板（弹层，不算导航层）
                 ├─ 今日待办（调度引擎推送）
                 └─ 留痕 / 快照 / 质疑（右侧面板）
```

**深度 = 3**（首页 → 对象列表 → 时间线）。事件录入是弹层/抽屉，不占导航层，避免「点进点进再点进」。

---

## 3. 管理端 IA（配置 + 治理，2 层为主）

content-manager 侧栏下，一个「**NHP 研究管理**」导航分组，内含三小组：

```
管理端 sidebar
  └─ NHP 研究管理（导航分组）
       ├─ 📊 研究总览（/nhp-overview）        ← 总入口（§4）
       ├─ 采集侧运维（桥）
       │    ├─ 对象列表（/nhp，同门户）
       │    └─ 实例管理（/nhp-records）
       ├─ 配置组
       │    ├─ 事件类型（/nhp-events）          [列表→详情 2 层]
       │    ├─ 字段字典（/nhp-fields）          [列表→详情 2 层]
       │    ├─ 码表（/nhp-codelist）            [列表→详情 2 层]
       │    ├─ 访视/时点（/nhp-visits）         [单页]
       │    ├─ 编码规则（/nhp-idrules）         [单页]
       │    ├─ 事件规则（/nhp-event-rules）     [单页]
       │    └─ 标准库（/nhp-standards）         [单页]
       └─ 治理组
            ├─ 字段审核（/nhp-field-review）
            ├─ 码表审核（/nhp-codelist-review）
            ├─ 快照管理（/nhp-snapshots）        [列表→对比→回滚]
            ├─ 审计留痕（/nhp-audit）            [双 tab]
            ├─ 数据质量中心（/nhp-quality）      [看板+事件队列]
            └─ 团队与权限（/nhp-team）
```

**深度规则**：
- 有「主实体」的页（事件类型/字段/码表）→ 列表→详情 2 层。
- 治理/辅助多是「看板/队列」→ 单页（数据质量、审计、团队）。
- 快照 → 列表→对比→回滚，但「对比/回滚」是抽屉/内嵌，不占导航层。

## 4. 总入口：NHP 研究总览（替代旧 hub）

**要不要总入口？要。但不是「4 步流程引导」，是「状态看板」。**

旧 `nhp-hub` 错在「引导你怎么配」（表单范式：配置模板→登记→开填）。新总览的价值在「告诉你现在什么状态 + 该去哪」：

```
📊 NHP 研究总览（管理端首页）
├─ 研究状态卡：对象数 · 事件类型发布 X/Y · 字段校对进度 43% · 码表当前版本 · 方案/panel 版本
├─ 待办/预警：数据质量事件 N · 待校对字段 N · 待复核 N · 待签署 N · CoC 断裂 N
├─ 快捷入口：去采集侧 · 配置组 · 治理组 · 双轨导入
└─ 最近动态：最近字典变更 · 最近快照 · 最近质控事件
```

它是**配置侧 + 治理侧 + 采集侧的聚合点**，也是「从管理端跳到采集侧代填」的桥。DM 每天从这一页进，不用翻 sidebar。

## 7. 看板 = 病例看板（团队/手术臂/病例，v11 修正 v10）

**v10 修正**：v10 把「角色」当第一维度是错的——真正的组织维度是「手术臂/团队」（心脏移植臂 vs 体外肝灌注臂），角色只是病例内的第二维度。

**层级（三层）**：
1. **手术臂 = 团队**：心脏移植臂（心脏团队 ↔ D9）· 体外肝灌注臂（肝脏团队 ↔ D10）——不同手术的不同团队靠「臂切换器」隔离。
2. **病例**：本臂的多个病例（心脏臂 3 例 / 肝灌注臂 1 例），每病例 = 受体+移植（或灌注事件），病例墙卡片列表。
3. **角色**（病例内）：PI 看校对/复核、兽医看照护、护士看给药——只过滤「待办类型」，不决定看哪组病例。

**病例墙（核心）**：每病例卡片 = 受体 + day0 + 当前时点 + 状态 + 今日待办 + 预警，点击进时间线。同一团队的同一手术 = 病例墙里多张卡片。

**数据模型提示**：需落「臂/团队」标识——建议 22 补 `crf_arm`（臂码 + 手术类型/器官 + 协议引用 D9/D10 + 团队角色），或 `crf_subject`/`crf_transplant` 挂 `arm_code`（HEART/LIVER），否则「哪个病例属于哪个臂」查不出来。

**在哪看**：门户侧对象列表 = 一线看板（已按臂过滤）；管理端 = 臂级病例看板（DM 跨臂、PI 单臂）。

**角色过滤仍保留（第二维度）**：

| 维度 | 过滤什么 |
|---|---|
| arm/团队 | 病例集：心脏臂只看心脏移植病例，肝脏臂只看肝灌注事件 |
| role | 待办类型：PI 看校对/复核、兽医看照护、实验室看回传 |
| capability | 动作可见性：`crf:verify` 才见复核、`crf:freeze` 才见冻结、`crf:query` 才见查询 |
| DAG | 数据范围：只本中心（SJ/SH） |

**角色 → 视图矩阵**（同框架，内容不同）：

| 角色 | 状态卡 | 待办/预警 | 快捷入口 |
|---|---|---|---|
| 平台DM | 全量（对象/校对进度/质控/版本） | 全局质控事件 + 全量待校对 + 待签署 | 全部 |
| 心脏PI | 心脏相关（D9 校对 + D3/D5/D6/D7 心脏复核） | D9 待校对 + 心脏待复核 + 签署（心脏） | 字段审核(D9) · 事件类型 |
| 肝脏PI | 肝脏相关（D10 校对 + D4 肝功能复核） | D10 待校对 + 肝功能待复核 + 签署（肝脏） | 字段审核(D10) |
| 兽医 | 本中心动物照护 | 今日该采血/给药/体征的动物 | 去采集侧 |
| 护士 | 本中心给药/体征任务 | 今日给药/体征待办 | 去采集侧 |
| 受托实验室 | 待回传结果 | TAT 待回传 + CoC 断裂 | 去采集侧（回传结果） |

> 实现：看板 widget 的数据源统一走「读侧查询」（22 §6.4 listTodoBySubject/listSeries 等），查询入参带 `(role, dagId)` 过滤；后端不区分「谁的页面」，前端按 capability 控制入口可见性。复用既有 RoleEnum+capability 两层权限（02 权限体系）。

## 8. 导航重构 + 布局方法论（v13 修正 v9/v12）

### 8.1 导航：顶栏「NHP研究」= 业务入口，内容管理 = 配置

```
顶栏（一级）
├── 首页
├── NHP研究  ← 业务操作面（干活的人：实验者/兽医/护士/PI）
│    ├── 📊 总览驾驶舱（落地页）
│    ├── 🧪 进入工作台（采集工作台/时间线）
│    ├── 🐾 采集侧 · 对象列表（/nhp）
│    └── 📋 审核中心（字段校对/复核/签署，按身份加载对应内容）
├── 内容管理  ← 配置运维面（管系统的人：DM）
│    ├── 配置组：事件类型 / 字段字典 / 码表 / 访视时点 / 编码规则 / 事件规则 / 标准库
│    └── 治理工具：快照管理 / 审计留痕 / 数据质量中心 / 团队权限 / 版本管理
└── 系统设置
```

**关键修正**：审核（字段校对/复核/签署）**从内容管理移到 NHP研究 入口下**——审核是业务操作不是系统配置；符合身份的人进入即加载对应内容（PI 看 D9、兽医看照护），不埋在后台。

### 8.2 布局方法论 + 设计哲学（v13 修正，落地为可复用规范）

**病根**：v9-v12「先造组件再往上拼」，且列不等高、卡片不撑满，导致对不齐、乱。

**布局铁律（4 条，实现无关，换颜色/框架同样适用）**：
1. **网格优先**：先划网格（如 12 列、gap 16px）分区，再填组件——不先造组件再拼。
2. **列等高**：`align-items:stretch`，每列总高度一致（列与列对齐，不参差）。
3. **卡片撑满列 + 内容加权**：卡片 `flex:1 1 auto`——2 张各占 50%、3 张分摊；内容多的卡保留自然高度占更多，剩余卡平分剩余空间。
4. **统一卡片结构**：header/body 同宽、同内边距、同结构。

**设计哲学（优先级从高到低，贯穿全 NHP 前端）**：
1. **一眼看全**：关键指标 / 审核通知 / 待办 / 质控 一眼可见，不埋进子页。
2. **下钻而非跳页**：详情页是「点卡片下钻」，不是「指标唯一可见处」。
3. **业务操作 vs 系统配置分离**：审核/采集走「NHP研究」业务入口，配置走「内容管理」。
4. **同框架 + 身份过滤**：一个看板框架，内容按 (arm/role/capability/DAG) 过滤，不每人一套页面。
5. **形态由数据性质定**：序列→网格、台账→列表、一次性事件→面板，不由「域」定。
