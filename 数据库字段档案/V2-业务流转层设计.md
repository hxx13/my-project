# V2 业务流转层设计

> 状态：设计 · 2026-08-22
> 前置：V2-架构总纲.md（五层正交 · 三×三事件模型）已落地「填表层」
> 本文定义采集架构的**第二层——业务流转**：阶段推进 / 审核放行 / 台账序列录入
> 范围：架构决策 + 接口契约（不写实现代码）

## 背景：填表层已完成，缺业务流转层

已完成：表单纯净化、事件指派矩阵、事件驱动采集、事件引擎接线（记录完成→展开随访）。

缺口（用户确认）：
1. **阶段推进**：生命周期没有推进机制，无法「进入下一个阶段」；
2. **审核放行**：填写后没有复核/放行的操作入口，没有业务流编辑能力；
3. **台账/序列**：PANEL（长表单）可用，LEDGER（台账）/SERIES（序列）是空壳，缺实体/序列录入层。

---

## 一、阶段推进（生命周期状态机）

### 1.1 状态机

```
SCREENING(预筛) → MATCHING(配型中) → POST_TX(移植后) → ENDPOINT(终点)
```

数据：`crf_subject.lifecycle_stage`（V38 已有列，API 已可设置）。

### 1.2 推进的两种来源

| 来源 | 触发 | 例子 |
|---|---|---|
| 手动推进 | 采集侧「推进阶段」操作 | 复核人员手动把对象推进到下一阶段 |
| 事件驱动 | 事件引擎 `ADVANCE_STATE` 动作（当前 no-op，需实现） | 配型通过 → SCREENING→MATCHING；手术完成 → MATCHING→POST_TX |

### 1.3 合法转移（状态机约束）

- `SCREENING → MATCHING`：配型通过（XM 决策 = 采用）
- `MATCHING → POST_TX`：手术完成（TX 记录提交 + tx_date 确立）
- `POST_TX → ENDPOINT`：终点/剖检

### 1.4 接口契约

- 后端：`POST /nhp/subjects/{id}/advance-stage`（body: `{ targetStage, operatorId, note }`），校验合法转移，写审计。
- 后端：`NhpEventEngine` 的 `ADVANCE_STATE` 动作从 no-op → 真推进（读 `action_spec.target_state`，调 `updateLifecycleStage`）。
- 前端：采集侧（`NhpSurgeryProgress`）加「推进阶段」入口，下拉选下一合法阶段。

## 二、审核放行（关键事件复核/放行）

### 2.1 现状（可复用，不重复造）

记录状态机已存在：`DRAFT → COMPLETE → REVIEWED → SIGNED → LOCKED`；
快照（`crf_record_snapshot`）、签名（`crf_signature`）、审计（`crf_data_audit_log`）均已实现。

### 2.2 缺口与设计

缺口：采集侧没有「复核/放行」的 UI 动作入口；「放行」业务概念（供体放行判定）没有码表承载。

设计（**复用现有能力，只补 UI + 一个码表引用**）：
- 工作台顶栏在「提交」后增加动作：**复核通过（REVIEWED）→ 放行/签署（SIGNED）→ 锁定（LOCKED）**，直接调已有 `updateStatus`/`sign`，自动打快照 + 审计。
- 「放行判定」字段（D1.04）引用码表（如 `RELEASE`：放行/待定/不放行），落 EAV 值；判定结果驱动「是否允许推进下一阶段」。

### 2.3 接口契约

- 复用：`PUT /nhp/records/{id}/status`（REVIEWED/SIGNED/LOCKED）、`POST /nhp/records/{id}/sign`。
- 新增：无（复用现有）；仅前端补 UI 动作入口。

## 三、台账 / 序列录入（实体 + 序列数据模型）

### 3.1 三种数据模型（对齐三×三事件模型）

| 形态 | 数据模型 | 存储 | 现状 |
|---|---|---|---|
| PANEL 面板 | 单条结构化记录 | EAV `crf_record_value` | ✅ 可用 |
| LEDGER 台账 | 重复子实体（样本/给药/AE） | 实体表 `crf_sample`/`crf_medication`/`crf_adverse_event` | ❌ 空壳 |
| SERIES 序列 | 测量序列（指标×时点） | EAV + concept 聚合（`listSeries` 已有） | ⚠️ 只读网格 |

### 3.2 LEDGER 台账录入

- 后端：样本/给药/AE 实体 CRUD 端点（`crf_sample` 等实体表 + mapper 已建，缺 Controller/Service）。
- 前端：`NhpLedger` 从「只加不减」补成「增删改」，接实体端点；每条实体自动取号（`NhpIdService`，已有）。

### 3.3 SERIES 序列录入

- 后端：批量连录接口 `upsertSeries`（22 §6.4 已规划，未实现），行=时点、列=指标，时间戳自动递增。
- 前端：`NhpSeriesGrid` 从「只读」补成「可编辑」，接 `upsertSeries`；异常值按 `crf_reference_range` 高亮。

### 3.4 接口契约

- `POST /nhp/samples`、`POST /nhp/medications`、`POST /nhp/adverse-events`（+ GET/PUT/DELETE）——实体 CRUD。
- `POST /nhp/records/{id}/series`（body: `{ rows: [{ recordedAt, values }] }`）——批量连录。

---

## 四、实施顺序（依赖驱动）

1. **阶段推进**（最小，直接回答「如何进入下一阶段」）：`advance-stage` 端点 + `ADVANCE_STATE` 真推进 + 前端入口。
2. **审核放行**（复用现有快照/签名/审计，只补 UI + 码表引用）。
3. **台账/序列录入**（最大，实体 CRUD + 批量连录）。

每步验收：后端编译 + `tsc -b --noEmit` + 浏览器走查。
