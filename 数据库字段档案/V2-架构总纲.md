# V2 架构总纲（REDCap 对齐）

> 状态：V2 权威骨架 · 2026-08-22
> 唯一事实：**码表 + 字段**（源自《异种移植 NHP 数据字典》Excel）
> 参照范式：**REDCap 表单流程**（成熟可参考）+ **实验动物实际流程**（业务特有）
> 归档：`V1/`（此前全部探索性设计，含 event_anchor×frequency、capture_form 那一套）

## 一、为什么 V2（V1 的病根，一句话）

V1 把「表单结构」和「何时使用表单」焊死在同一个对象里——`event_anchor` / `frequency` / `capture_form` 全塞在表单上，导致三个后果：

1. 表单不再纯粹，编辑器和调度引擎互相纠缠；
2. 探索性的压缩编码（锚点 × 频次）不可解释、不可维护；
3. 把「怎么渲染」（SERIES/LEDGER/PANEL）错当成「表单的固有属性」。

V2 只保留一件事：**表单是表单，调度是调度，值域是值域。**

## 二、核心原则：五层正交

| 层 | 是什么 | 谁产出 | REDCap 对应 |
|---|---|---|---|
| ① 字段字典 | 字段「是什么」（字段 + 码表引用） | 源 Excel（唯一事实） | Data Dictionary |
| ② 表单 Instrument | 字段「怎么收集」的一组结构（+ role） | 编辑器 | Online Designer 产出的 form |
| ③ 事件 Event | 命名时间点（入组 / 手术 / 术后第 N 天） | 配置侧「事件定义」 | Define My Events |
| ④ 表单-事件指派 | 矩阵：哪个表单在哪个事件出现 | 配置侧「指派」 | Designate Instruments for Events |
| ⑤ 状态机 + 调度 | 对象生命周期 + 把事件展开成待办 | 调度引擎 | Arms + Scheduling + Record Status |
| （正交）码表 | 字段能填哪几个值 | 源 Excel（唯一事实） | Select choices / 受控词表 |

**关键：④ 才是「表单何时出现」的唯一答案，它跟表单自身无关。**

## 三、关键决策（ADR）

1. **表单不携带任何调度信息。** 编辑器产出的表单只含：字段集合 + 码表引用 + role（PK/FK/DERIVED/VALUE）。`event_anchor` / `frequency` / `capture_form` 从表单上移除。

2. **事件是第一公民。** 时间是显式的命名事件（TP01~TP12 可作初始事件集），不再用「锚点 × 频次」的压缩编码。

3. **表单-事件指派矩阵决定「何时出现」。** 一个表单可指派到多个事件，一个事件可挂多个表单。

4. **码表只做值域，不参与调度。** 码表是字段的取值约束，与「何时出现」正交。

5. **高频重复是事件的属性，不是表单的属性。** 实验动物特有的「术中每 5 分钟 / 术后每日」，表达为事件的「重复规则」（节奏 + 窗口），挂在事件上。

6. **生命周期状态机独立驱动活跃事件。** 对象阶段（预筛 / 配型 / 移植后 / 终点）决定当前哪些事件活跃；状态推进由事件触发（如「手术完成」→ 进入移植后），不手填。

- **码表**（受控词表：FARM / BREED / ORG / …）
- **字段**（249 字段 / 13 域 / 数据类型 / 单位 / 必填 / 码表引用）

## 五、开放问题（仍在摸索，逐条收敛）

1. 事件重复规则如何表达高频（术中每 5-15min、术后每日、血药谷峰）——REDCap 无此原生能力，需实验动物扩展。
2. 生命周期状态机的阶段，与事件的对应粒度（一个阶段挂几个事件）。
3. 是否保留 Arm（臂 / 研究分组 HEART/LIVER）。
4. 「表单-事件指派」是显式矩阵，还是按「事件 → 默认挂哪些表单」的规则推导。
5. 高频序列（监护 / 检验趋势）在采集侧的呈现（网格 / 台账 / 面板），归「渲染」还是归「事件类型」。
